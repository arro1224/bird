## 一、执行结论

### 1.1 一句话判断

当前项目已经具备一个“能够展示拍鸟盒子连接、照片审阅和复制任务概念”的原型，但尚不具备稳定交付 P0 的条件。

### 1.2 当前成熟度

| 维度 | 评分 | 直接评价 |
|---|---:|---|
| 产品定位与核心流程 | 6/10 | 主方向正确，但首页、图库、批次、任务的职责仍有混淆 |
| UI 与交互完成度 | 5/10 | 已有统一风格，但仍存在固定演示数字、空按钮、假筛选和不完整操作 |
| 功能闭环 | 5/10 | 多数页面可进入，部分操作没有形成真实结果闭环 |
| 数据一致性 | 4/10 | 主要依靠全局刷新广播，不是明确的单一数据源 |
| 真实盒子联调准备 | 4/10 | 有 `/api/v1` 草案，但接口状态码、事件、冲突和下载契约未锁定 |
| 离线能力 | 5/10 | 审阅/批量操作可排队，但任务控制和复制任务未真正离线闭环 |
| 性能与稳定性 | 5/10 | 已修过刷新死循环，但仍有广播刷新、轮询与重复请求风险 |
| 测试与验收 | 3/10 | 只有少量模型/Cubit 测试，几乎没有 Widget、集成和真机自动验收 |
| 可发布程度 | 3/10 | 更接近演示版，尚不能视为可靠 P0 产品 |

综合判断：

- 演示原型完成度：约 70%。
- 可联调 P0 完成度：约 50%。
- 可交付真实用户的完成度：约 35%。

### 痛点 4：数据同步依赖“全局广播刷新”，容易重复请求和状态抖动

当前 `SessionRefreshCoordinator` 发出一个 generation，设备、批次、图库和任务页面分别重新请求。问题是：

- 无法说明究竟哪类数据发生变化。
- 一个照片操作可能导致设备、批次、图库、任务全部请求。
- IndexedStack 中未显示页面也保持订阅。
- 任务详情同时使用事件订阅、4 秒轮询和全局刷新。
- 已经发生过设备状态与全局刷新互相触发导致卡顿的事故。

这套方案适合原型，不适合继续扩展。

### 痛点 6：离线同步只完成了一半

- 用户离线点击任务控制，产品没有统一策略。
- 创建复制任务失败后没有真正的重放机制。
- 待同步操作之间没有资源级顺序和依赖关系。
- 同步失败没有提供用户可管理的失败列表。

建议明确产品规则：

- 审阅、标签：允许离线排队。

## 四、建议的目标架构

### 4.1 数据层原则

每一类核心资源只允许一个权威 Store：

| 资源 | 建议 Store | 消费页面 |
|---|---|---|
| 设备连接 | `DeviceSessionStore` | 全局横幅、首页、设置、诊断 |
| 当前设备状态 | `DeviceStatusStore` | 首页、诊断 |
| 批次 | `BatchStore` | 首页、批次入口、复制确认 |
| 照片/审阅 | `PhotoReviewStore` | 图库、单图、分组、对比 |
| 任务 | `JobStore` | 首页任务摘要、任务中心、任务详情 |
| 同步队列 | `PendingSyncStore` | 设置、诊断、离线提示 |

页面 Cubit 负责组合和展示，不再各自重复维护同一个资源副本。

### 4.2 事件更新原则

- 服务端事件先进入 Store。
- HTTP 操作成功后把返回结果直接合并 Store。
- 仅对未知/丢失事件做定向刷新。
- 禁止一个通用 refresh 信号让所有模块一起请求。
- 所有资源包含 `updatedAt` 或 `version`。

## 十、最终产品经理意见

当前项目最大的误区，是把“页面已经画出来”和“功能已经实现”混为一谈。现在最不应该做的是继续增加更多页面；最应该做的是删除假数据、修复假入口、统一数据源、锁定盒子契约，并用端到端测试证明核心流程真的成立。

当以下三件事完成后，项目才适合继续做大规模视觉精修：

1. 审阅结果在图库、分组、批次之间始终一致。
2. 任务状态在首页、任务中心、详情之间始终一致。
3. 模拟盒子和真实盒子通过同一份契约测试。

在此之前，UI 越精致，越容易掩盖产品闭环尚未完成的事实。

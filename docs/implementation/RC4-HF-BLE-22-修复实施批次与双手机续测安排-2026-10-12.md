# BLE-22 修复实施批次与双手机续测安排

制定日期：2026-10-12（北京时间）。依据当前工作区、BLE-22 暂停记录和第 8～10 轮结果制定。

建议先完成 BLE-22A、22B 两批离线准备，在 BLE-22C 接回华为和 vivo 做阻塞问题定点复测；通过后进入 BLE-22D、22E 的完整双手机预验收。BLE-23 生成板端交接包，真实 BirdBox 到位后进入 BLE-24。

2026-10-12 实施更新：BLE-22A、22B 的离线修改和检查已完成，已准备最终第 12 轮四种 APK；原生 150 项、Flutter 定向 58 项、PowerShell 工具 24 项和 Python 工具 8 项通过，相关静态分析无问题。详见 [实施与离线验证记录](RC4-HF-BLE-22A-22B-实施与离线验证记录-2026-10-12.md)。下一批为 BLE-22C 接回两机定点复测。

以下为分批要求；手机测试继续保持暂停，BLE-22 尚未通过，真实盒子仍为 `hardware_status=pending`、`releasable=false`。

## 1. 当前判断与优先级

| 项目 | 当前事实 | 本轮处理 |
| --- | --- | --- |
| vivo 已绑定后的安全 GATT 重建 | 第 8、9 轮已连接，但停在服务发现，15 秒内没有有效服务发现回调；发生在认证故障注入之前 | 第一优先级；先补调用证据，再用手机定位与修复 |
| SDK≤28 服务发现前等待 1 秒 | 原生回归通过；第 10 轮停在安装确认，没有 BLE 实测 | 待验证兼容调整；有效性尚未确定 |
| 旧连接清理与 ATT 超时恢复 | 第 7 轮首片、中片、末片实测通过；后续推广后的最新候选尚未完整通过 | 保留历史证据，在新候选上复测 |
| 通知重建故障注入 | 已调整为初始订阅成功后，在安全重建第二路 CCCD 失败；原生回归通过 | 补真机场景，确认实际进入目标故障阶段 |
| 测试安装、早期失败材料 | vivo 安装需要系统确认；扫描、初始连接/订阅等早期失败可能没有 App 导出；运行器外层清理不完整 | 第二优先级；补可重复操作与失败留存 |
| 正式 UI、权限、验证码、保存/分享 | 现有生产代码和本地回归不能代替手机页面验收；当前集成入口只导出连接事件 | 两机补正式入口、完整诊断和 P3/P4 验收；依据失败改动 |

华为 FIN-AL60（Android 12 / SDK31）与 vivo X20（Android 8.1 / SDK27）均已实际启动五特征 GATT Server 并取得广播成功回调。当前失败不能据此登记为手机不支持 BLE 外设。

已完成的本地检查为 App 原生 140 项、虚拟外设原生 40 项、Flutter 定向 38 项及相关静态分析。它们是当前自动检查记录，不代表最新候选已经通过双手机无线链路验收。历史各轮 APK 不同，成功次数不能跨构建合并。

## 2. 实施顺序

| 批次 | 主要工作 | 手机要求 | 进入下一批的条件 |
| --- | --- | --- | --- |
| BLE-22A | 补服务发现调用证据与早期失败导出 | 无需连接 | API 未调用、拒绝、异常、无回调及取消等结果可区分，相关回归通过 |
| BLE-22B | 整理安装/操作/证据工具，准备正式入口测试流程 | 无需连接 | 工具可留存启动失败、可回收自有资源，待测构建身份明确 |
| BLE-22C | 双手机定点复测，定位并修复 vivo 安全重建阻塞 | **首次接回两机** | 重建稳定进入服务、MTU、两路通知；目标故障场景能被实际执行并取得预期结果 |
| BLE-22D | 冻结修复候选，完整 P1/P2 BLE 验收 | 两机均连接 | 每方向首次至少 5 次、已绑定至少 5 次，故障和生命周期矩阵通过 |
| BLE-22E | 正式 UI、P3/P4、完整文件保存与分享验收 | 两机均连接 | 权限/设置、验证码/HTTP 页面、成功与失败文件回传均有真实记录 |
| BLE-22F | 汇总同一候选的结果，核定 BLE-22 门禁 | 通常无需持续连接；缺项需补测 | 可用组合无未解决关键失败，所有要求有实际状态与证据 |
| BLE-23 | 同步版本/构建/验收工具，制作板端联调包 | 最终包核验时连接 | 最终 APK 与报告身份一致，必要设备回归通过，接收方可离线校验 |
| BLE-24 | 两手机分别与真实 BirdBox 联调 | 真实盒子和两机到位 | 真实安全链路、AP/STA、HTTP 身份/会话和文件回传闭环通过 |

BLE-22A～22F 是原 BLE-22 的子批次；原 BLE-23、BLE-24 的编号和职责保留。

## 3. BLE-22A：补服务发现与早期失败证据

主要文件：

- `android/app/src/main/java/deckers/thibault/aves/BirdBoxBleChannel.java`
- `android/app/src/test/java/deckers/thibault/aves/BirdBoxBleBridgeTest.java`
- `integration_test/ble11_dual_avd_test.dart`
- `integration_test/ble22_phone_test.dart`
- 对应诊断事件保留策略与证据校验器。

实施内容：

1. 在已有 `gatt_services_discovered`、阶段失败和延迟开始事件基础上，补实际 `discoverServices()` 调用时刻、同步返回结果和异常分类。关联当前请求、连接代次、GATT 代次及阶段耗时，区分「没有调用」「调用被拒绝」「调用已接受但无有效回调」。对因归属或阶段不符而丢弃的回调保留必要的有界诊断。
2. 保留对外错误码语义，通过诊断说明真实失败原因；服务属性不匹配和无回调不能混为一种事实。继续执行五特征、属性与 CCCD 校验。
3. 将测试证据收集覆盖到扫描、连接、初始订阅和安全准备失败，确保在受保护命令之前失败也能保存实际事件和真实 JSON/ZIP。未发生的写入、绑定或响应保持未发生状态，校验器拒绝将早期失败登记为成功。
4. 对上述行为补必要回归：同步 false、异常、无回调、取消等待、旧回调、导出失败。沿用有界终止和一次恢复规则。

本批不凭推测增加兼容等待或恢复次数。当前 1 秒服务发现等待保留为待实测假设，在 BLE-22C 决定是否保留、调整或撤回。

退出条件：本地生产桥回归、相关 Dart 测试和静态分析通过；可从失败文件定位实际停止阶段。

## 4. BLE-22B：整理双手机运行与操作工具

主要文件：`tool/ble22/run_phone_round.ps1`、`tool/ble22/` 下操作与文件核验工具、两种集成入口及正式 UI 操作说明。

实施内容：

1. 将当前 `build/` 中临时操作、接收文件校验和汇总助手整理为可维护的工具；清理构建目录后仍能复现测试。
2. 将安装、外设启动、VM 发现、转发创建和测试执行纳入完整异常/清理流程。安装拒绝、广告未启动、VM 无法连接等均生成结构化失败记录；只清理本轮拥有的转发和进程。
3. 补有界的安装与测试请求处理：检查已安装 APK hash；确认已识别的测试 APK 安装页面、两测试设备间系统配对请求及应用按钮；未知弹窗留存状态并停止该轮。系统 PIN 不使用应用验证码替代。
4. 将 transport 自动授权模式与正式 UI 权限测试模式明确区分。权限拒绝、永久拒绝与设置返回需要真实系统交互，不能用 `-g` 或 `pm grant` 作为通过证据。
5. 准备 transport、正式 `lib/main.dart`、模拟 `lib/main_bird_simulated.dart` 的构建及安装清单。三个入口分别记录包身份和 APK hash，虚拟外设另记 hash。模拟入口使用 `BIRD_SIMULATED_DEVICE_ID`。
6. 固定双向角色切换步骤：退出上一轮 App/外设、核对广播与服务、记录两端测试 bond 基线。临时可发现设置单独登记，避免将测试外设设置变成产品手工预配对要求。

源码改动后建立新轮次；第 10 轮 APK 的结果仍保持「未进入 BLE 测试」。本批通过后即可通知接回两机，无需等待全部后续批次完成。

## 5. BLE-22C：第一次接回两机，做阻塞问题定点复测

接入前需要 BLE-22A、22B 的相关检查通过，待测 APK 已生成并登记 hash；接入时核对设备型号、序列号和安装包实际 hash。

首先恢复 vivo 本任务临时修改的 `log.tag.flutter`、`log.tag.DartVM` 为原始空值；核对残留转发的归属。上一轮拔线后这两项日志设置未成功恢复。

定点测试顺序：

1. **P2：vivo App → 华为虚拟外设**。先跑普通已绑定连接，定位服务发现是否实际调用、是否被接受以及回调是否抵达。再跑 `auth_once`，必须分清普通安全准备失败与真正进入认证恢复后失败。
2. 结合两端日志验证当前 SDK27 等待是否有效。若仍失败，围绕调用顺序、旧连接释放、回调归属、外设服务生命周期与绑定条件提出最小改动；每次改动新建轮次，并先复测触发失败的场景。以日志确认的事实决定修复方向。
3. 服务重建可完成后，复测一次认证恢复、持续认证失败有界终止、ATT 首/中/末片超时及修正后的通知重建失败。确认故障注入实际命中了目标阶段。
4. **P1：华为 App → vivo 虚拟外设**。验证正常连接及受影响的恢复场景，检查 SDK31 路径有无回退。
5. 两方向补首次绑定定点检查：记录两端未绑定基线，观察系统请求从 App 流程出现，确认成功、取消和超时的实际结果。只处理明确属于本测试的绑定。

退出条件：正常安全准备和应恢复场景可完成；预期终止场景在正确阶段有界失败；取消后的旧请求不能继续。若仍有关键失败，本批继续修复，不进入完整通过统计。

这批是双手机定位与修复复测，尚不是完整预验收。两台手机分别交替承担 App 与虚拟外设角色。

## 6. BLE-22D：完整 P1/P2 BLE 验收

在 BLE-22C 关闭关键阻塞后冻结待验收候选。记录源码指纹、build_id，以及 transport、正式 App、模拟 App、虚拟外设各自的 hash；同一入口在该候选内保持同一 APK。

P1、P2 每方向执行：

- 首次未绑定至少 **5 次**，已有绑定重连至少 **5 次**；两方向共至少 **20 次正常完整路径**，另外执行故障与生命周期场景。初始 bond 以两端实际状态为准。
- 小 MTU；一次认证恢复；持续认证终止；ATT 首片、中片、末片超时；通知重建失败；对端断开；延迟、错误 ID、重复业务响应；业务响应超时。
- 系统配对取消、页面取消、前后台/锁屏返回、对端退出、连接中关闭蓝牙及重新扫描。
- 检查同请求恢复、代次归属、通知就绪后再写、一次恢复上限及业务去重；保留成功和预期失败的真实文件。

集成入口证据用于原生传输与故障验证；正式 App 还需通过 BLE-22E 页面操作。BLE-22C 的记录只有在候选身份、场景和操作完全符合要求时才能计入，不合并旧轮次成功次数。

## 7. BLE-22E：正式 UI、P3/P4 与完整导出

本批先实测现有流程，按实际失败修复对应页面、Cubit、网络仓库或诊断实现。

| 组别 | 两机分别执行的内容 | 验收证据 |
| --- | --- | --- |
| 正式 App → 手机虚拟外设 | 页面扫描、选择、首次/已有绑定、验证码交互、配对/页面取消、前后台返回 | 正式入口截图/日志和对应请求；与集成入口结果分别记录 |
| P3：birdSim → HTTP Mock | 错误验证码→正确验证码、AP/STA 模拟终态、`/health` 身份、会话兑换、首页三 Tab | 两机使用独立新 Mock 会话，记录真实 HTTP 和页面结果 |
| P4：正式 App 无外设 | 权限拒绝/永久拒绝、位置关闭及设置返回自动扫描、蓝牙关闭重试、扫描取消/超时 | 使用真实系统界面及正式入口，无自动授权替代 |
| 完整诊断 | 成功/失败的扫描及连接历史，导出、保存、分享、取消与重试 | 接收端解析实际 JSON/ZIP，独立计算 SHA-256 并核对内容范围 |

P3 的网络状态模拟及 adb reverse 仅覆盖相应 App/HTTP 业务；真实 AP/STA/DPP、手机路由与盒子网络服务保留到 BLE-24。

若本批修复生产代码，更新冻结轮次并复测受影响项目；涉及 BLE、配对或共同生命周期逻辑时，重做相应 P1/P2 验收，最终报告不拼接不同候选的通过结果。

## 8. BLE-22F、BLE-23 和 BLE-24

BLE-22F 汇总每个方向、场景、次数、构建身份和文件校验结果。只有可用组合不存在未解决关键失败，要求的场景均有真实结果，才能结束 BLE-22。原 MIS-AL00、OPPO 和真实盒子的缺项单列 pending。

BLE-23 按原主计划执行：同步 BLE-12 旧版本默认值和硬件验收的先绑定规则，采用高于 176 的 versionCode，生成正式 APK、构建清单、自动/手机报告、协议对照、诊断样例、板端操作和回传模板、离线校验入口。完成候选的全量检查及必要设备回归。版本/打包生成了新 hash 时，对最终安装包进行身份核验和关键路径复测；涉及生产逻辑修改时重做受影响的验收矩阵。交接包不得直接标为已经完成真实硬件验收，也不自动推送或联系板端。

BLE-24 在交接包准备好且真实盒子到位后开始。板端先核对固件、五特征/通知/MTU、绑定条件、SMP/IO/Agent 与密钥持久化；随后华为、vivo **分别与真实盒子连接**，完成首次绑定、重连、取消/超时、盒子重启/密钥丢失、安全恢复、实际 AP/STA、HTTP 身份/会话及首页闭环。是否支持多手机同时连接另由产品和固件能力确定。

现有两机可以开始实盒联调，但不能代替原报告中的 MIS-AL00 与 OPPO 最终复测。真实硬件门禁满足后才能调整发布状态。

## 9. 何时连接手机

1. **现在至 BLE-22A、22B 完成：** 可以继续保持两机拔线，执行离线修改与检查。
2. **BLE-22C 开始：** 第一次接回两机，安装明确构建并验证当前 vivo 阻塞；这是最早需要双手机的节点。
3. **BLE-22C 通过、候选冻结后：** 开始 BLE-22D、22E 完整双手机预验收。预计工作量包括至少 20 次正常 BLE 路径及故障/UI/文件场景，按实际结果安排，不承诺未验证的完成日期。
4. **BLE-23 完成、板端提供真实盒子后：** 开始 BLE-24 双手机与真实盒子联调。

BLE-22A、22B 已完成；建议下一条实施指令为「实施 BLE-22C」。进入该批时接回两机并继续真机测试，本次离线实施没有自动恢复此前暂停的运行。

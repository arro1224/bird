## 保留策略

连接 journal 继续使用 v4 缓存键，内部增加 `retention_schema_version: 2`，导出仍为 schema 4，新增字段保持兼容。默认全局上限如下，不按 flow 无限累加：

| 对象 | 上限 |
| --- | --- |
| 连接记录 | 500 条 |
| 单个 journal 的完整 UTF-8 JSON（含计数和元数据） | 2 MiB |
| 受保护的最近请求 | 4 个，按 `flow_id + request_id`，没有 request 时使用 attempt_id |
| flow 损失统计 | 128 个，超出后明确历史未知 |

`BleCriticalEventPolicy` 覆盖用户配对、receiver 注册、createBond 调用/返回/异常、bond 变化、GATT 重建、服务/MTU/CCCD 恢复、敏感写 API/回调/超时/重试、命令业务结果、取消/终态和 teardown。含 error_code 或 terminal_outcome 的记录也视为关键。请求的各 ATT 写子步骤共享父请求保护，不因分片消耗多个保护名额。

普通观察优先从最旧记录裁剪；其次是保护窗口外的关键记录。窗口内关键记录也受条数和字节上限约束，不承诺无限保存。当前 attempt 的首个关键事件及终态尽量作为锚点；容量连锚点都无法容纳时仍须释放记录并登记损失。跨请求、跨 flow 的旧失败记录不再因新请求的普通高频流量直接消失。扫描 journal 也有字节上限，但没有连接关键请求保护。

旧缓存迁移从现存记录建立保护窗口。旧统计已经丢记录、却不能判断丢失是否关键时，`critical_history_unknown: true`，不补造历史。

导出 `retention.connection_events` 增加：

- `critical_observed`、`critical_retained`、`critical_dropped`：在已知历史内满足 observed = retained + dropped。
- `critical_events_missing`：关键损失或历史未知时为 true。
- `critical_missing_reasons`：`critical_event_capacity`、`older_request_window`、`byte_capacity`、`persistence_write_failure`、`history_unknown`。
- `maximum_protected_requests`、`maximum_journal_bytes`、`retained_journal_bytes`：明确容量边界。

普通记录被裁剪时，raw_history_complete 可为 false，而 critical_events_missing 仍为 false；二者回答不同的完整性问题。false 仅表示本日志已观察并计数的关键记录没有已知损失，不能证明无线链路上未记录的事件或板端事实。

写失败仅累计真实 storage.write 失败。失败记录的损失在本进程立即可见，后续成功写入将计数原子落盘，重建 store 后继续可见。若存储持续不可写并直接杀进程，尚未落盘的计数无法恢复；本批没有跨进程恢复 pending 绑定或把未落盘事件补造为事实。

## 调用计数和失败阶段

| 字段 | 定义 |
| --- | --- |
| create_bond_call_count | 在生产平台即将调用 createBond 时递增；实际重复调用分别计数，false 和异常也计数 |
| command_attempt_count | 受保护命令第一次进入写阶段为 1；唯一允许的恢复重试进入写阶段为 2；准备配对阶段为 0 |
| att_write_call_count | 当前父请求真实 writeCharacteristic API 调用总次数；分片、重试、false 和 API 异常分别计数 |
| write_fragment_index | 当前命令尝试内的 ATT 调用序号；进入下一次命令尝试时清零，再从 1 递增 |
| preparation_step / failure_phase | 准备链当前子步骤及失败前阶段，便于区分绑定、连接、服务、MTU 和通知恢复 |

保留既有 security_write_attempt_count 兼容字段。计数不保存 SSID、密码、token 或写入 payload。协调器的 create_bond_invoked 提示不再重复增加计数，真实平台调用边界发出该事件。

原生桥回归验证两个分片成功、第三个 API 返回 false 仍为一次命令尝试、三次 ATT 调用；恢复后重试为两次命令尝试、两次 ATT 调用，重试分片从 1 开始。createBond false 分支计数为 1，受保护 ATT 调用为 0。

## 文件和截止点

capture 同步向两个 journal 入队 snapshot barrier，纳入 barrier 之前完成入队且最终保留的记录；后到回调属于下一次导出。排序与完整记录输出不改变该截止点。失败缓存写入会反映在 retention；诊断异常被业务边界隔离，不推进或终止配对。

沿用生产 BirdBoxDiagnosticFileWriter 的临时文件、完整写入、哈希校验、原子改名及有界缓存。小文件为 JSON，大于 256 KiB 的完整 JSON 使用 ZIP。ZIP 只含 summary.json、full_trace.json、README.txt，summary 和完整记录的 trace、构建、retention 应一致。

JSON 的文件 hash 与 payload hash 相同。ZIP 的 payload hash 针对 full_trace.json，最终文件 hash 针对 ZIP 的实际字节；README 只记录 payload hash，最终 ZIP hash 通过 App 独立展示，避免内嵌自身最终 hash。

原生文件通道新增可注入 worker，用于执行生产 prepare/save/onActivityResult 路径的测试；MethodCall 从其他线程进入时先回到主线程处理状态。生产保存仍先校验缓存，再写入用户选择的 content URI，最后重新打开该 URI 读取并计算哈希，匹配后才返回 saved。取消、重复导出、保存忙、写入失败、缓存损坏、接收文件损坏、生命周期中断均有回归。系统分享返回 share_opened，仅证明选择器打开，不证明接收成功。

## 交付样例与接收端

同目录 ble19-samples/ 中交付：BirdBox_BLE_synthetic_local.json、BirdBox_BLE_synthetic_local.zip、verification.json。样例由 Dart 生产 snapshot/export 路径生成，随后通过生产 Java 文件 writer 写出，再由独立 Python 工具重读。每条连接记录 source 为 synthetic_local_test；构建标识、计数为测试占位值，不对应真实 APK 或手机实测。verification.json 明确 phone_acceptance: false。

| 文件 | 字节 | 保留连接记录 | 最终文件 SHA-256 |
| --- | --- | --- | --- |
| JSON | 9876 | 17 | 14cbc233211938b33762124d6c58dcafc1d47672fdcd7e5384eb40e978365374 |
| ZIP | 8193 | 500 | 7f8d58f39f77854cc1dbf35f1ac3123383195a8b4cfc34439433477189276509 |

ZIP payload SHA-256 为 `0bce6bd4300ad8658f7531ff56bf9443c4af7ed364cd8ebde925b062cfc029b7`。

接收端执行（Python 3 标准库，无额外安装依赖）：

```powershell
python tool/ble19/verify_diagnostic_file.py <实际收到的JSON或ZIP路径> --sha256 <从App独立抄录的最终文件SHA256> --require-critical-complete
```

退出码 0 为文件/结构校验通过且无已知关键缺失；1 为完整性或结构错误；2 为文件可读但关键记录缺失。去掉 --require-critical-complete 时，缺失关键记录的文件仍可作为失败排查材料，报告继续明确缺失。

需要重新生成本地样例时，在项目根设置 BLE19_SAMPLE_DIR 指向 build/ble19/samples，执行 BLE19 Flutter 测试；用 javac 编译生产 BirdBoxDiagnosticFileWriter.java 和 tool/ble19/WriteDiagnosticSamples.java，随后运行 deckers.thibault.aves.WriteDiagnosticSamples 并传入上述样例目录。file-manifest.json 提供生产 writer 的文件 hash，接收端仍需实际读文件计算，不能仅复制 manifest 作为校验结果。

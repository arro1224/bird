### 当前配对竞态的可复现事实

`BirdBoxPairingCoordinator.start()` 先用第一次 `bondState()` 初始化状态，再注册 receiver，然后按第二次读取执行动作。第一次为 BONDED、第二次为 NONE 时，会调用 createBond，但状态仍停在 BONDED_RECOVERING_GATT；绑定广播和绑定 timer 因 `isWaitingForBond()` 为 false 而被忽略。

本轮对当前 HEAD 重新编译生产协调器和状态机运行探针，结果为：

```text
createBondCalls=1, phase=BONDED_RECOVERING_GATT, rebuilds=0, failure=null, active=true
```

探针位于本地忽略目录 `build/ble-analysis/PairingRaceProbe.java`，仅用于复现。BLE-17 必须将用例转为正式原生回归测试，不能依赖 build 目录作为长期证据。这是当前代码缺陷的复现，不是对 175 真机失败分支的追溯证明。

## BLE-17 绑定状态初始化和推进修复

目标：状态机的内部阶段与本次读取的真实 bond 一致，每个 attempt 都有明确结果。

主要文件：

- `android/app/src/main/java/deckers/thibault/aves/BirdBoxPairingCoordinator.java`
- `android/app/src/main/java/deckers/thibault/aves/BirdBoxSecurityWriteStateMachine.java`
- `android/app/src/main/java/deckers/thibault/aves/BirdBoxBleChannel.java`
- `android/app/src/test/java/deckers/thibault/aves/BirdBoxPairingCoordinatorTest.java`

实施内容：

1. 建立 attempt owner 并清理旧等待，注册 receiver 后重新读取真实 bond；以同一次有效读取结果初始化状态并选择 NONE、BONDING、BONDED 分支。未知状态确定失败。
2. 对注册前后 bond 丢失、快速完成、同步返回与广播先后变化建立一致处理。已有绑定不重复 createBond；NONE 分支每个 attempt 最多调用一次。
3. 将绑定等待是否结束作为明确事实，不能仅因阶段异常就忽略绑定期限。绑定期限只覆盖绑定阶段，完成后由 GATT 各阶段期限接管，不能误杀已在重建的流程。
4. 确保 receiver、timer、取消与 GATT 回调串行推进；终态幂等，pending result 只完成一次。
5. createBond 返回 false、权限异常和其他异常必须保留原始失败分类；未完成安全准备时受保护写入次数为零。

回归矩阵：首次 NONE、已有 BONDING、已有 BONDED、NONE→BONDING/BONDED、BONDED→NONE/BONDING、未知状态、false、异常、重复广播、取消后晚广播、旧 owner 超时、绑定中旧 GATT 断开。

退出条件：原复现用例不再停滞；上述矩阵有确定结果；Android 相关原生测试、App Java 编译及相关 Flutter 安全准备回归通过。保留先绑定主路径，不退回首次写入触发绑定。

交付：正式回归用例、修改记录、实际测试报告和状态转换说明。

## BLE-18 生命周期归属和原生桥验证

目标：把现有 Dart 页面保护延伸到真实原生通道，明确 Activity、Engine、页面和进程边界。

主要文件：`MainActivity.java`、`BirdBoxBleChannel.java`、`provisioning_cubit.dart`、`platform_birdbox_ble_data_source.dart`，以及对应原生与 Flutter 测试。

实施内容：

1. 系统配对弹窗、短暂 inactive/paused 和后台切换保留 attempt；用户取消只结束所拥有的 attempt。旧页面不能关闭新连接。
2. 明确 Activity 重建的策略：保持 Engine/session 的场景继续原生 attempt 并重新接入 UI；真正 Engine 销毁时明确终止，记录生命周期原因和阶段。进程重启只读取真实系统 bond 并启动新请求，不复用旧 pending request。
3. 审核 `cleanUpFlutterEngine()` 与 `dispose()` 的调用顺序及重复清理。禁止把生命周期清理映射成 network_internal_error，禁止结束后 UI 无限等待。
4. 在原生桥中建立可替换的最小平台边界，用于控制 GATT、bond 读取、广播与调度。保留生产副作用路径；测试不得仅直接调用纯状态机来证明桥已执行。
5. 验证注册监听在 createBond 之前、旧 GATT 被隔离、新服务和两路 CCCD 恢复完成后才允许写入、每个 Result 只回调一次。

需要注入的故障：createBond false/异常、广播缺失、连接失败、服务错误、MTU 回调缺失、第一/第二路 CCCD 失败、写回调迟到、权限撤销、取消与回调竞争。

退出条件：相关生命周期回归通过；原生桥测试能证明上述副作用顺序。Instrumentation 中只有错误码分类断言不算完成；设备侧执行状态单独登记，不能把“编译成功”写成“执行通过”。

交付：生命周期行为表、原生桥回归、阶段化错误和取消记录。

## BLE-19 关键诊断保留和文件回传

目标：失败文件能够回答是否调用绑定、调用结果、状态如何变化，以及谁结束了流程。

主要文件：`ble_diagnostic_journal.dart`、`ble_connection_diagnostic_store.dart`、`ble_diagnostic_snapshot_service.dart`、`ble_connection_diagnostics.dart`、`BirdBoxBleDiagnosticFileChannel.java`、`BirdBoxDiagnosticFileWriter.java` 和对应测试。

实施内容：

1. 对当前 attempt 和最近有限数量终态 attempt 保护关键事件链，普通高频观察优先裁剪。保护集合和存储字节均须有上限，不能无限保留。
2. 必须保留 user_start_pairing、receiver 注册、createBond 调用/返回/异常、bond 变化、GATT 重建、通知恢复、安全写/回调/超时/重试、业务响应及取消/teardown。采用事件保留或独立 attempt 事实汇总，并使两者一致。
3. 若关键记录因故无法保留，显式输出 critical_events_missing 和原因，不能通过普通 retained_count 暗示证据完整。
4. 写入次数、命令尝试次数和分片次数分别定义；真实 createBond 调用计数在实际副作用边界更新，不能靠布尔去重隐藏重复调用。
5. snapshot 包含截止点之前全部保留记录。失败保存、缓存上限、取消系统选择器及重复导出不影响绑定流程。
6. 校验 JSON 与 ZIP；ZIP 必含 summary.json、full_trace.json、README.txt。区分 payload SHA-256 与最终文件 SHA-256，接收端重新读取计算，不能让文件内嵌自身最终 hash。

验收：制造超过 500 条连接事件的压力记录，关键链仍可解析；覆盖跨 attempt、裁剪、写入失败、snapshot 并发和重启读取。华为和 vivo 各完成分享或保存后的接收端独立校验，并记录系统分享打开不等于接收成功。

交付：保留策略、压力回归、脱敏 JSON/ZIP 样例、文件校验记录。

## BLE-20 新配对流程的虚拟外设和证据校验

目标：虚拟外设及工具验证先绑定主路径，并能注入已绑定后的有限恢复故障。

主要文件：`android/virtualBirdBox`、`tool/ble11`、`tool/ble12` 的场景定义与校验器，以及 `ble11_simulated_evidence_test.dart`、`ble11_virtual_box_isolation_test.dart` 等测试。

实施内容：

1. 提供加密权限的主成功场景，不能将开放写权限的普通成功等同于安全写成功。保持虚拟外设 debug/test-only 与生产依赖隔离。
2. 新场景至少包含首次绑定、已有绑定、绑定后认证错误一次、绑定后认证错误持续、指定分片无响应、通知订阅失败、断链、延迟/错误/重复业务响应。
3. 故障注入有明确目标：characteristic、分片序号、首次或持续、错误 status、延迟。首片、中间片和末片分别覆盖，不能只在完整消息后注入。
4. 更新证据规则：正常首次成功是 createBond 一次、GATT 重建、通知就绪、第一次命令尝试成功，不要求 fallback 或重试；已有绑定分支 createBond 为零；异常恢复最多一次，不能循环。
5. 相同请求恢复保持 request_id 和命令内容一致；新 MTU 允许重新分片，不能要求不同 MTU 下每片字节完全一致。分别核对重组消息与实际分片限制。
6. 外设验证业务去重，不能在同一 request_id 的重试中重复产生操作。响应延迟与 ATT 写确认区分：无 ATT 响应用于写超时；有 ATT 响应但无业务事件用于业务超时。
7. 原生 API 同步 false、权限异常、完全缺失广播等不能可靠由远端制造的故障，放在 BLE-17/18 测试边界中验证，不伪造为手机外设实测。
8. 增加独立的手机虚拟外设证据类型；双 AVD 的 netsim/PCAP 要求只适用于 AVD 运行器，不强套到华为/vivo 运行器。

证据建议记录 security_flow=bond_first、endpoint_kind=virtual_birdbox、手机型号、构建、attempt/request/generation 及事件序列。schema 版本应更新，旧证据按旧规则读取，新候选不再沿用旧断言。

退出条件：场景单测、证据正反例与工具隔离检查通过；至少一个可用环境能执行主成功和一次恢复场景。模拟器环境缺失如实登记，不把下载升级作为所有 App 代码实施的先决条件。

交付：场景操作入口、双手机运行方式、更新后的校验器和实际模拟证据。

## BLE-22 华为与vivo手机预验收

2026-10-12 续测规划：双手机测试按用户要求暂停，最新候选尚未通过。后续拆为 BLE-22A～22F：先补诊断与工具，在 BLE-22C 接回两机定位 vivo 服务发现阻塞，关闭关键失败后执行完整预验收。具体实施内容与接机节点见 [修复实施批次与双手机续测安排](RC4-HF-BLE-22-修复实施批次与双手机续测安排-2026-10-12.md)；历史结果保留在 [暂停记录与续测清单](RC4-HF-BLE-22-双手机预验收暂停记录与续测清单-2026-10-12.md)。

目标：使用现有手机验证正式 App 原生 BLE 路径和诊断操作，记录可验证的边界。

BLE-22A、22B 离线实施更新：服务发现 API/回调分类、早期失败导出、安装/操作/文件核验工具及四入口构建准备已完成；原生 150 项、Flutter 定向 58 项、PowerShell 工具 24 项、Python 工具 8 项及相关静态分析通过。最终准备轮次为第 12 轮，尚未安装或测试手机。详见 [实施与离线验证记录](RC4-HF-BLE-22A-22B-实施与离线验证记录-2026-10-12.md)；下一批为 BLE-22C，不据此将 BLE-22 或真实盒子登记通过。

前置：BLE-18 至 BLE-21 的必要代码检查通过；同轮测试固定 App 与虚拟外设 APK hash。修改源码后重新构建并生成新的测试轮次，不能合并不同构建的成功事件。

第一步检查两台手机的蓝牙开启状态、BLE 广播能力、GATT Server 启动和实际广告成功回调。API 存在不等于两机都支持外设角色。

| 组合 | 手机角色 | 验证重点 |
| --- | --- | --- |
| P1 | 华为运行正式 bird App，vivo 运行虚拟外设 | Android 12 Nearby 权限、位置兼容、绑定和新 GATT 写入 |
| P2 | vivo 运行正式 bird App，华为运行虚拟外设 | Android 8.1 位置权限、旧 API 路径、绑定和恢复 |
| P3 | 两机分别运行 birdSim，连接本地 HTTP Mock | 验证码/网络业务模拟、HTTP 身份、凭据和页面 |
| P4 | 两机分别运行正式 App，执行无外设环境操作 | 权限、位置提示、扫描取消、超时、文件导出和清理 |

每个可用 BLE 组合执行：

- 首次未绑定完整路径，至少 5 轮；已有绑定再次连接，至少 5 轮。
- 位置关闭→引导→设置返回自动扫描；拒绝权限、永久拒绝后的设置返回、蓝牙关闭重试。
- 系统配对取消、页面取消、后台/锁屏恢复、对端退出、手机关闭蓝牙和连接后重新扫描。
- 小 MTU、一次安全写恢复、持续错误终止、写确认与业务响应分别超时。
- 成功和失败完整导出，接收端解析及 SHA-256 核对。

首次未绑定测试需要明确两端 bond 基线。仅清 App 数据不能证明系统 bond 已清除；测试人员可以清理测试手机的既有绑定，但产品正常使用流程不能要求用户到系统页手工配对。

结果按场景、轮次、构建、角色保存。若某机不能广播，反向组合支持则继续执行；两边均不支持时，手机 BLE 链路标记 unsupported，继续软件与 P3/P4 验证，将缺口带到板端。没有原 MIS-AL00 或 OPPO 时，保持各自 pending，不以 FIN-AL60/vivo 替代。

退出条件：可用组合无未解决关键失败，全部场景有真实状态；不支持的组合有能力检查证据。设备 BLE 失败须修复后重测，不能借“真实盒子待验收”忽略本地 App 缺陷。

交付：手机预验收矩阵、录屏/截图、脱敏 App 与虚拟外设日志、完整导出及校验记录。

## BLE-23 构建工具同步和板端交接包

目标：让板端获得身份明确、规则一致、一次失败就能回传有效材料的候选。

主要文件：`tool/release/build_android_apks.ps1`、`tool/ble12/build_ble12_candidate.ps1`、`ble12_candidate_validator.dart`、验收模板、BLE-16/04/05 等相关校验工具和手册。

实施内容：

1. 修复 BLE-12 写死的 1.14.8/172、文件名和校验默认值；从 pubspec、APK Manifest 和真实构建元数据读取，三者不一致拒绝打包。虚拟外设版本也读取实际构建。
2. 同步正式硬件验收的先绑定口径。现 BLE-16 T1 强制 same_request_retried_once，T3 强制旧错误码，T4/T5 以 A/B 作为最终流程，均须更新或建立版本化的新候选规则。保留历史记录的语义，不把旧证据改写成新通过。
3. 主成功分支重试次数为零；已绑定异常分支才检验恢复一次；绑定 timeout、写 callback timeout 和业务 response timeout 分别记录。
4. 生产 APK、安装 APK、构建 manifest、运行时诊断的 package/flavor/version/commit/build_id/source_fingerprint/hash 一致。以实际日志解析测试计数，不硬编码 20、66 或 207 等历史数量。
5. 候选整合所有批次后采用高于 176 的 versionCode；具体 versionName 按仓库发布规则确定。最终候选尽量从已提交干净源码构建；dirty 开发包必须明确标记并附指纹，不冒充提交构建。
6. 不将当前历史 176 APK 的旧 build_id 与新 HEAD 混用。产物目录按构建身份区分，保存源文件清单、APK hash 和验证报告。
7. 区分 App 预验收与真实硬件发布门禁。建议 handoff_readiness 使用 ready、ready_with_gaps、blocked；存在已知关键 App 缺陷时必须 blocked。手机外设能力不足可 ready_with_gaps，但须列出未验证场景。
8. 真实盒子尚未验收时 hardware_status=pending、releasable=false，不能为了生成联调包解除发布门禁。App 预验收状态、手机 BLE 结果与真实盒子结果分别保存。

交接目录至少包含：

```text

build/                构建 manifest 源文件 hash APK hash 权限与签名说明
reports/              自动测试与华为 vivo 预验收报告
diagnostics/          与当前候选一致的成功和失败脱敏文件
protocol/             RC4 UUID 属性 通知 分片 命令响应 身份校验对照
```

退出条件：重新构建并运行全量 Flutter 测试、静态分析、App/虚拟外设相关原生测试及必要设备测试；每项有实际执行状态。接收者能离线校验产物、识别版本、执行步骤和填写回传。外部环境缺口单列，不能把未执行登记为 passed。

## BLE-24 真实BirdBox和原目标手机联合验收

目标：板端在同一 App 候选和明确固件上完成真实安全链路及配网闭环。执行方为板端和现场手机测试人员，App 开发根据完整回传修复已定位问题。

开始前双方核对：

- 固件版本、BlueZ/适配器状态、PairingAgent/IO 能力、可绑定条件、已有 bond 与设备密钥保存策略。
- App 在 open_pairing 前调用 createBond 时，盒子已允许 SMP 绑定；若盒子必须另有物理操作开启可绑定窗口，双方明确正常产品流程。
- 五个特征、加密/认证权限、两路通知、实际 ATT MTU 和 RC4 分片一致；应用验证码与系统蓝牙交互分开。
- 盒子重启、固件升级或清除 bond 后如何恢复；不要求 App 静默删除系统绑定或传入固定系统 PIN。

真实验收场景：

1. 原华为 MIS-AL00 位置关闭引导及开启后的扫描恢复。
2. 原华为与 OPPO 首次未绑定：user_start_pairing→createBond→BONDING/BONDED→新 GATT→通知恢复→安全写→pairing_opened→应用验证码。
3. 已绑定再次连接、用户拒绝、绑定停滞、bond 丢失、盒子重启和手机蓝牙关闭。
4. 绑定后安全写异常的一次恢复和持续失败终止，确认板端业务去重。
5. 直连 AP 与 STA 的网络操作终态、实际手机路由、/health 身份与临时会话兑换，进入正式业务页面。
6. 同一失败轮次成功回传 App JSON/ZIP 和板端日志，能够关联时间、请求、固件及构建。

每轮采用统一 run_id 并记录 UTC 时间与时间偏差；App 的 request_id/attempt_id/generation 与板端实际接收的 request_id 对照。system bond 阶段尚无 RC4 请求时，以轮次、时间和设备关联，不能虚构板端 request_id。

故障定位按层推进：无 raw 结果查扫描；createBond false 查手机 API/权限；已 BONDING 后失败查双方 SMP；已 BONDED 但 GATT/CCCD 失败查重建；写已 ACK 但无 pairing_opened 查协议；配网终态后 HTTP 失败查实际路由和服务。采集必要的 BlueZ/btmon，不能统一归因于 App 或板端。

退出条件：原目标双机与真实盒子完成要求的闭环；完整文件可解析且构建身份一致；关键失败关闭并在同一修复候选上重测。只有真实硬件证据满足发布门禁后，才允许晋级 releasable。

## 检查执行和交接规则

每批实施记录统一包含：基线与结束提交、涉及文件、实际行为、测试命令/环境/结果、证据路径/hash、未完成项与下一批依赖。允许每批形成独立提交，不能自动推送、发布或联系板端。

按改动范围先运行相关检查，候选冻结时再完成全量检查。文档或工具规则改动使用对应校验器正反例；生产状态机改动必须有行为回归。不要用新增日志、模拟 BOND_BONDED 或延长 timeout 代替修复。

所有涉及凭据的测试采用专用测试值；生产诊断不保存 Wi-Fi 密码、应用验证码、完整会话、token 或完整 DPP URI。板端低层抓包可能包含链路标识或敏感内容，按双方调试渠道保管；可外发报告提供脱敏摘要和文件 hash。

首次执行从 BLE-17 开始。真实盒子联调待完成不阻止 BLE-17 至 BLE-23 的实施；本地测试环境缺失应记录并修复可控问题，不把软件缺陷推给板端。

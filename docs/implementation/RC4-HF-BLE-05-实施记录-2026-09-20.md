本批已形成可直接交给外场测试方的目录，并实现自动校验。当前结果是：

```text

returned_evidence_status=pending

releasable=false
```

这表示交接包自身完整，不表示 OPPO/Huawei/K7 已通过。当前仍只有 vivo，所以没有

## 3. 防止“测错包”

BLE-03 原门禁会验证证据里声明的 APK 文件和 SHA 一致，但外场仍可能重编译后把新
SHA 一起填入证据。BLE-05 增加第二层固定：

- A 必须为
  `2954EA9D4720B22B29B288C3A37EEF17A13FF2C75E2AB1213E19664920BE5108`；
- B 必须为
  `12E0E4F1AF0E7421D508908FAB24CB60FC6E9347FE81DB57C55D2FF8B4116AE8`；
- A/B 包名、扫描权限策略和 Git 基线必须分别匹配；
- 回传证据中的 `builds.A/B` 必须仍是上述交付二进制；
- 任何换包、损坏、错分支或只改 JSON 状态的回传都会阻断。

源码快照明确标记为 `uncommitted_hotfix_snapshot`。Debug 包只用于问题闭环，不能
升级为 Release，也不能绕过 BLE-04 的干净 Git、正式签名和审批要求。

## 4. 必测矩阵固化

交接清单固定要求：

- Huawei A/B 基线各 10 次；
- Huawei 最终候选包在 baseline、蓝牙重开、权限重授、前后台恢复各 10 次；
- OPPO 最终候选包扫描 10 次；
- OPPO PKC110/API 36 首次配对 5 次；
- 真实 K7、同请求 App/K7 日志、已配对重连和任务不中断；
- App、板端和 QA 审批。

vivo、模拟器、系统蓝牙页截图或口头成功说明均不能计入。

## 5. 回传校验

```powershell
dart run tool/acceptance/rc4_hf_ble_05_handoff_gate.dart `
  --manifest=outputs\RC4-HF-BLE-05\handoff-manifest.json `
  --returned-evidence=<回传证据JSON>
```

工具先校验交接包，再执行 BLE-03 的全部扫描、配对、K7、重连、审批和脱敏规则，
最后复核回传 APK SHA 与交付包一致。只有两层都通过才输出：

```text
status=verified
hardware_status=verified
next_gate=RC4-HF-BLE-04
releasable=false
```

`releasable` 仍为 false，因为正式包策略落地、签名、干净提交、审批和回滚属于
BLE-04。

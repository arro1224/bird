## 4. 问题清单、原因与解决方案

### P0-01 正式 BLE 配网成功页无法完成跳转

**实施更新：已由 RC4-B1 完成代码修复与自动化验收，待真实 K7 验收。**

**证据**

- `lib/bird_companion/app/app_router.dart:77-82` 创建 `ConnectionPage` 时只传入 `entryMode` 和 `provisioningRepository`；
- `lib/bird_companion/features/connection/presentation/pages/network_provisioning_page.dart:255-258` 在 `onCompleted == null` 时禁用“完成”；
- 正式路由没有其他地方注入 `onProvisioningCompleted`。

**影响**

用户即使已经完成 BLE、Wi-Fi 和 `/health` 校验，也无法从正式页面进入相册、AI 和任务页面；这与交接图“校验同一盒子后进入图片/AI/任务页面”不一致。

**解决方案**

1. 把完成结果从单独 `Uri` 升级为包含 `deviceId`、`baseUri`、`networkMode` 的安全值对象；
2. 在正式完成处理器中调用 `ConnectionRepository.connect()` 获取业务 `DeviceStatus`；
3. 调用 `DeviceSessionCubit.setConnectedFromStatus()`，确保 REST、WebSocket、缓存命名空间和离线同步处于同一个设备上下文；
4. 初次设置进入 Shell，设置页“添加/切换”按 `entryMode` 返回适合的业务页；
5. 为正式路由增加端到端 Widget 测试，禁止只在测试 harness 中传回调。

### P0-02 页面销毁会释放 Direct AP 的 Android Network 绑定

**实施更新：已由 RC4-B1 完成代码修复与自动化验收，待真实 Android + K7 验收。**

**证据**

- `ProvisioningCubit.close()` 调用 `_repository.disconnect()`；
- `ProvisioningRepositoryImpl.disconnect()` 先执行 `_wifi.releaseNetwork()`，再断开 BLE；
- 成功后导航离开会销毁两个 Cubit，从而触发上述清理。

**影响**

在蜂窝网络仍为默认路由的 Android 手机上，刚通过校验的 BirdBox Direct AP 可能立即失去进程网络绑定，后续 REST、WebSocket 和图片请求改走蜂窝网络并失败。

**解决方案**

1. 拆分“停止扫描”“断开 BLE”“释放 Direct AP 网络绑定”“彻底 dispose”四种生命周期动作；
2. 页面正常完成时只停止扫描，可按策略保留 BLE，并必须保留 Direct AP Network 绑定；
3. 用户取消/切换设备时才断开 BLE；只有离开 Direct AP、收到网络丢失或 App 终止时才释放 Network；
4. 将 Wi-Fi Network 绑定提升为 App 生命周期资源，由会话协调器或独立 `BirdBoxNetworkBindingCoordinator` 管理；
5. 增加回归：完成并进入 Shell 后，Direct AP 请求仍绑定同一 opaque Network handle。

### P0-03 Release 门禁没有校验 rc4 真机配网矩阵

**证据**

- `docs/acceptance/ble-provisioning-rc4-real-device-evidence.template.json` 的真机模板仍使用 `SIM-01`～`SIM-10`；
- `tool/release/run_b7_gate.ps1` 的 Release 分支只校验通用 real-box 11 项业务 E2E 和 B12-B；
- 脚本没有消费上述 rc4 真机模板，却在 Release 成功分支直接写入 `real_k7_status = "verified"`。

**影响**

在未来外部基线补齐后，Release 门禁可能在没有验证 BLE 加密、AP/STA 回滚、DPP、动态地址和断线恢复的情况下给出错误绿灯。

**解决方案**

1. 真机证据 ID 改为 `K7-01`～`K7-10`，与 A7 审计表一致；
2. 新增专用 fail-closed 验证器，检查：真实 Android、真实 K7、Release 签名、App/固件 SHA、一致的 `device_id` 摘要、每项 passed 和非空脱敏证据；
3. Release gate 新增必填 `-BleRc4EvidencePath`，在构建 Release APK 前后都验证证据与 APK/证书/基线一致；
4. 只有专用验证器通过后才能写 `real_k7_status=verified`；
5. 增加负向测试：缺项、SIM ID、Debug APK、模拟器、错误 SHA、敏感字段、空证据都必须失败。

### P0-04 盒子端与业务后端源码、版本和负责人缺失

**证据**

`docs/contracts/birdbox-v1-baseline.json` 当前为 `blocked_external_inputs`，以下字段为空：盒子仓库、分支、固件 SHA、部署命令、数据库版本、迁移/回滚、集成地址和四方联系人。本仓库也没有 `birdbox_network` 或 `birdbox_api` 源码。

**影响**

无法证明或修复：设备 ID 原子持久化、NetworkManager 回滚、DPP Enrollee、AP DHCP、Unix Socket 授权、PairingCodeProvider、网络状态文件、日志脱敏和板端 180 秒恢复命令。

**解决方案**

1. 先获取两个盒子端仓库及冻结固件 SHA；
2. 由协议 owner、App owner、盒子 API owner、QA owner 签字确认 rc4 字段与验收矩阵；
3. 盒子端分别跑单元、集成和 K7 实机用例；
4. 全部证据齐全后再更新 `birdbox-v1-baseline.json`，禁止用占位值解除阻断。

### P1-01 Wi-Fi 二维码只有领域模型，没有用户流程

**实施更新：已由 RC4-B2 完成代码修复与自动化验收，待真实相机与 K7 验收。**

**证据**

- `WifiQrCredentials` 和 `ProvisioningMethod.wifiQr` 已存在；
- 现有扫码页解析的是“设备连接地址二维码”，不是标准 `WIFI:` 凭据二维码；
- `NetworkProvisioningPage` 只有“搜索附近 Wi-Fi”“手动输入 Wi-Fi”“使用 DPP 安全配网”三个卡片，没有“扫描 Wi-Fi 二维码”。

**影响**

未满足冻结协议和交接图规定的三种 STA 入口。DPP 不可用时只剩扫描和手动，二维码兜底缺失。

**解决方案**

1. 新增严格的标准 `WIFI:` payload 解析器，支持转义字符、隐藏 SSID、开放/WPA2/WPA3 映射；
2. 新增专用 Wi-Fi 二维码扫码页，不复用设备地址二维码结果类型；
3. 扫描后只在内存保留密码，默认遮挡，确认提交后立即清空 controller/扫码结果；
4. 转换为 `WifiQrCredentials.toStaNetworkConfiguration()`，确保 `provisioning_method=wifi_qr`；
5. 增加合法、转义、未知安全类型、空 SSID、无密码受保护网络和敏感信息不落日志测试。

### P1-02 DPP 按钮展示前没有完成手机能力门控

**实施更新：已由 RC4-B2 完成代码修复与自动化验收，待真实 Android + K7 DPP 验收。**

**证据**

页面 `onTap` 只判断 `capabilities.dppUsableByBox`。手机 API 29、`isEasyConnectSupported()`、系统 Activity 可处理 Intent 等条件在点击后才由 Repository 检查。

**影响**

不支持 DPP 的手机仍会看到可点击按钮，点击后才失败；不符合协议“全部条件成立才显示可点击入口”的规则。

**解决方案**

1. 给 `ProvisioningRepository` 增加不含秘密的 `getDppAvailability()`；
2. `openWifiProvisioning()` 异步加载盒子与手机合并能力，增加 `checkingDppAvailability` 状态；
3. 页面根据最终能力显示“推荐”、隐藏或置灰，并给出统一说明；
4. 点击时 Repository 仍需二次检查，防止能力在页面停留期间变化；
5. 增加 API<29、Easy Connect=false、Activity 缺失、盒子=false、AKM 不支持和能力变化测试。

### P1-03 “断开盒子直连”设置路径与分支反馈不完整

**实施更新：已由 RC4-B3 完成代码修复与自动化验收，待真实 Android + K7 验收。**

**证据**

- 成功页只有“停止盒子直连”，点击后立即执行，没有协议指定的确认框；
- 设置的“网络诊断 → 切换网络”实际跳到设备管理页，而不是网络配网页；
- 没有固定“设备设置 → 网络设置 → 断开盒子直连”入口；
- `DirectApStopped`、恢复 STA、恢复同一 AP、无保存 STA、`NETWORK_RECOVERY_FAILED` 没有按协议逐项区分展示。

**影响**

用户可能误触导致图片传输短暂中断，也无法知道盒子最终恢复到了哪个网络；设置页无法完成交接图中的“断开直连并恢复原 Wi-Fi”。

**解决方案**

1. 新建正式网络设置页，进入时通过 BLE 读取 `get_network_status`；
2. 仅在 `active_mode=direct_ap` 时启用“断开盒子直连”；
3. 使用协议冻结的副标题与二次确认文案；
4. 固定发送 `stop_direct_ap(restore_previous_sta=true)`；
5. 收到 `command_accepted` 后显示进度，禁止立即成功；
6. 分别处理：`sta_connected + /health`、`network_recovered(direct_ap)`、`direct_ap_stopped(no_saved_sta_profile)`、`NETWORK_RECOVERY_FAILED`；
7. 将网络诊断页“切换网络”改为正式 BLE 配网入口，而不是设备管理页。

### P1-04 BLE 中途断开没有展示层自动恢复

**实施更新：已由 RC4-B3 完成同设备重连后的状态恢复、旧事件过滤和安全提示；自动重发现/重连仍归入 RC4-B4 原生稳定性范围。**

**证据**

Repository 内部有 `disconnects` 流且重连后会读取 `get_network_status`，但 `ProvisioningRepository` 接口没有暴露连接状态，`ProvisioningCubit`/`NetworkProvisioningCubit` 也没有订阅断开并执行重发现、重连和进度恢复。

**影响**

网络切换期间 BLE 抖动后，页面可能长期停在进度状态；用户只能退出重来，无法兑现“断开重连后恢复操作状态”。

**解决方案**

1. 在领域接口暴露不含平台句柄的 BLE 链路状态流；
2. 保存当前可信候选的最小重连信息，只按同一完整 `device_id` 恢复；
3. 使用有上限的指数退避重发现/重连；
4. 重连后强制 `get_network_status`，按同一 `operation_id` 恢复页面；
5. 超时后给出“保持盒子开启并重试”，不主动取消盒子端任务；
6. 覆盖切换中断、App 前后台、蓝牙开关、盒子重启、旧事件到达和用户主动取消。

### P1-05 Android 原生桥测试和错误语义不足

**证据**

1. `androidTest` 目前只有 `BirdBoxDppChannelTest.java`，没有 BLE 和 Wi-Fi 原生桥同级测试；
2. `BirdBoxBleChannel.isLinkEncrypted` 用 `BOND_BONDED` 近似链路加密状态，不能单独证明当前连接已加密；
3. `BirdBoxWifiChannel.onLost()` 只在原生侧解除绑定，没有通知 Dart 会话网络已经丢失；
4. `onUnavailable()` 统一映射为 `system_denied`，当前实现无法可靠区分用户取消、系统拒绝无互联网网络和超时；
5. 真实手机厂商兼容矩阵尚无证据。

**影响**

Fake 测试可能全绿，但真机仍可能出现敏感特征误判、断网不感知、错误提示不准确和厂商 ROM 行为差异。

**解决方案**

1. 增加 BLE 与 Wi-Fi instrumentation/Robolectric 测试；
2. 安全判断以盒子端 GATT characteristic 权限和真实读写失败为权威，`BOND_BONDED` 只作辅助状态；
3. Wi-Fi 原生桥增加 network lost EventChannel，驱动会话断线与重连；
4. 记录脱敏的系统结果类别，不记录 SSID 密码、Token 或完整 MAC；
5. 在 OPPO、vivo、小米、华为、荣耀、三星及 Android 近三大版本跑矩阵。

### P2-01 开发验证码提示与“禁止 App 写死”尚未形成一致方案

**证据**

`PairingCodeForm` 在 `fixedDev` 且无显示屏时只提示“请查看盒子提示”，没有交接材料要求的开发提示；同时协议禁止把 `123456` 写死在 App。

**解决方案**

1. 不在运行时代码或校验逻辑写死验证码；
2. 若开发包必须显示提示，使用仅 Debug/内部 flavor 注入的 `PairingInstructionProvider`；
3. Release 构建不得包含固定码文本，并增加二进制/源码门禁断言；
4. 量产只替换盒子端 `PairingCodeProvider`，App 继续依据 Device Info 的长度和显示能力展示通用文案。

### P2-02 Android-only 项目与冻结协议 iOS 要求冲突

**证据**

README 将项目定义为 Flutter Android 客户端，根目录没有 `ios/`，也没有 CoreBluetooth、NEHotspotConfiguration 或本地网络权限实现。

**解决方案**

- 若本期产品明确 Android-only：由协议 owner 出具范围补充，iOS 不计入本期发布承诺，但不得改写 rc4 事实；
- 若仍承诺 iOS：单独建立 iOS 实施批次，完成 BLE、热点加入、本地网络权限、无互联网网络、`/health.device_id` 和近三个 iOS 大版本验收。Android 的完成不能替代 iOS。

### P3-01 全量静态检查尚未归零

**证据**

`flutter analyze --no-pub` 当前因 `test/bird_companion/production_entrypoint_test.dart:34` 的 `prefer_single_quotes` 返回非零。

**解决方案**

只修复该测试字符串风格并复跑全量 analyze；不要顺带格式化或覆盖用户已有的 `pubspec.lock` 修改。

## 7. 推荐提交拆分

为降低回归风险，每个批次至少按以下粒度提交：

1. `test(rc4): add failing production completion/lifecycle coverage`
2. `fix(rc4): activate provisioned session and retain direct-ap binding`
3. `test(rc4): add wifi qr and dpp availability coverage`
4. `feat(rc4): add wifi qr and capability-gated dpp paths`
5. `test(rc4): cover stop-direct-ap outcomes and ble resume`
6. `feat(rc4): add network settings and operation recovery`
7. `test(android): cover ble and wifi platform bridges`
8. `fix(android): harden birdbox platform lifecycle`
9. `test(release): reject missing rc4 real-device evidence`
10. `build(release): require rc4 k7 evidence gate`

禁止把协议文件改动、App 功能、盒子端修复和真实证据一次性压成一个不可审查的大提交。

## 8. 每批次统一质量门槛

每批次至少执行：

涉及 Android 原生桥时增加：

```powershell

```

涉及发布时增加：

```powershell
powershell -ExecutionPolicy Bypass -File tool/release/run_b7_gate.ps1 `
  -Mode Release `
  -RealBoxEvidencePath <通用真实盒子证据> `
  -BleRc4EvidencePath <BLE rc4 K7-01到K7-10证据> `
  -B12BEvidencePath <B12-B证据>
```

验收报告必须明确区分：

- `simulated`：只用于回归和演示；
- `real_k7_pending`：尚未获得真实硬件全项证据；
- `verified`：专用证据 gate 全部通过；
- `releasable`：真实 K7、通用业务 E2E、B12-B、签名和批准全部通过。

## 9. 禁止事项与回滚原则

1. 不得把 Fake/Mock 页面作为 Release 入口；
2. 不得因 BLE 或 App 断开而取消盒子 AI 任务；
3. 不得记录或持久化验证码、pairing session、Wi-Fi/AP 密码、Token、完整 DPP URI；
4. 不得仅凭 Android `RESULT_OK`、系统 Wi-Fi 图标或手机自动重连判断配网成功；
5. 不得在未完成 K7 DPP 实机验收时把盒子能力改为 true；
6. 不得为三分钟调试租约给正式 App/公开协议新增字段；
7. 不得直接修改冻结 rc4 UUID、枚举、错误码和字段；如确需修改，先走协议版本与迁移评审；
8. 每个网络切换必须保留 previous/last_good 回滚路径；App 失败只显示安全结果，盒子端负责恢复网络。

### 自动接续存在四处结构性缺口

1. `features/jobs/domain/job_create_requests.dart:1` 的导入请求只有缩略图和预览参数，没有 `auto_analysis`。
2. `features/jobs/data/job_api.dart:55` 的导入结果仅为一个 `BirdJobStatus`。更早的 `core/network/api_client.dart:322` 会拆掉整个响应封套，只保留 `data`，因此同级 `workflow` 与 `analysis_job` 会在进入 JobApi 前丢失。
3. `features/tasks/presentation/repository_task_experience_controller.dart:329` 先创建项目，随后将识别或持续复制意图暂存在手机端，再发普通导入。`:585`、`:620`、`:628` 在导入完成事件和刷新路径补建识别或复制会话；手机关闭时这些回调无法承担接续。
4. 当前项目创建与导入调用没有将同一次开始操作的两个幂等键和完整请求在发送前持久化。网络层虽然支持幂等头，但默认每次调用生成新值，无法独立保证回包丢失、进程重启后的重放。

因此必须把请求、完整响应、持久化、盒子所有权判断与恢复查询作为一个完整接入范围。先删手机回调会丢接续；只加请求字段会引入重复建任务风险。

### 前台连接恢复

保留当前连接代次及防旧响应覆盖，补上取消的后继行为。每次使尝试失效都要明确取消来源、是否由新尝试接替，以及无接替时进入的失败、离线或等待网络状态。恢复页面的期限应覆盖整个用户可见恢复过程，不能随旧 Future 取消而失去约束。

网络判断需要区分手机作为 Wi-Fi 客户端、手机提供热点和盒子直连。热点宿主机可能只有蜂窝上游标签，应验证本地链路和同一盒子身份；真实 Wi-Fi 断开、授权失效仍需按现有策略降级。成功判据继续包括同一设备、受保护 HTTP 和实时连接验证。

复用现有诊断，增加取消发起者、原因、旧新 generation、attempt、后继动作、网络角色和期限结果。前后台回调保留为补充恢复入口，前台本身必须能够收敛。

### 批量审阅与离线筛选

批量接口使用明确命名的 `projectVersion`，单张详情继续使用照片或决策版本。针对一次选择提交一次批量请求，解析返回的项目版本；成功后刷新相关照片的真实版本，不能用项目版本给全部照片统一加一。

原基线的批次模型和 API 缺少权威项目版本读取链路。本次已增加可选版本模型、既有 current／项目列表兼容读取，现板是否返回该字段仍待后端确认。若公开响应未提供，需要后端补兼容字段或明确已有只读查询。App 对缺字段明确阻止批量修改，不虚构项目详情接口，也不靠试写制造 409 获取版本。

实施时按三个检查点推进：B2.1 固定项目版本读取契约并补模型／响应；B2.2 改在线批量、标签、真实照片版本刷新及离线旧记录重放；B2.3 改筛选即时投影。N14 开发收口必须包含 B2.2 的离线链路，不能只修在线保留按钮；B2.3 的 N11 页面工作不必阻塞 P0 阶段候选。

保留／弃选／未标记／精选／增删标签及离线重放统一改造。待同步记录增加版本作用域和格式标识；旧记录不能把照片版本直接解释成项目版本。保留用户意图和原快照，重新核对后再提交；遇到外部修改进入冲突流程，不能自动刷新版本后无条件覆盖。请求结果不明时沿用原键和原参数。

图库切换条件时，立即对当前缓存与待同步投影筛选，再呈现新结果；后台读取可继续，但不能把上一条件的照片作为新条件结果。缓存只有 60 张时，应表达“已缓存照片中的匹配项”，不能据此推断整个批次没有匹配照片。

同步修正模拟盒子的批次版本校验、成功回包和冲突夹具，使单张修改推进项目版本的场景能够真正暴露协议错误。

### BLE 恢复与 Wi-Fi 表单

将 BLE 恢复提示与直连 Wi-Fi 凭据档案解耦。无内存候选、无直连档案的已绑定 STA 盒子也可执行有时限、可取消的扫描；历史地址只是提示，最终以 `device_id` 验证。允许对同地址暂态失败按规则有限重试，保留现有会话所有权，恢复失败不释放有效业务网络。

查找页当前业务卡提供恢复 BLE 和重新查找入口，错误分别表达缺候选、权限拒绝、扫描超时、身份不符、授权问题等。

Wi-Fi 表单统一为确认连接信息。当前名称、盒子扫描结果、手动输入及盒子已保存配置分别标来源；扫描作为表单内子状态，失败和刷新不清空输入，明确换网后才清除旧网络口令。只在用户最终确认时下发一次加入操作。本机提供热点的入口保留人工确认或可用二维码，不承诺跨厂自动读取热点密码。

### 任务阶段与复制受阻

持续复制优先解释 `summary.blocked_kind`，兼容旧 `blocked_reason=COPY_INSUFFICIENT_SPACE`，未知情况显示通用存储受阻。仅显示有值的空间快照，说明它们是受阻时数据。重试使用原会话、当前 `expected_state_version` 和返回的 `allowed_actions`，不能新建复制任务绕过阻塞。

将 `job_type=sync` 的图片生成统一称为“准备浏览图片”，与离线审阅修改回写分开。图片准备不提供控制按钮，API 对过时客户端动作的拒绝也需要联调；AI 控制继续读取其自身 `available_actions`，本轮不增加板端尚未支持的运行期暂停／继续。

任务视图补上真实更新时间和进度时效，ETA 缺值保持未知，100% 尚未终态显示收尾。识别完成与图片准备完成分别表达，恢复先拉权威任务，再合并事件；迟到的完成事件只更新相应流程，不能抢走用户当前页面。

### 盒子自动导入识别

能力通过 `recognition-capabilities.import_analysis_workflow` 判断，持续复制另看 `smart_follow_available`。新增流程能力 DTO、完整导入结果和流程查询 DTO；沿用现有 Repository 与缓存，不另造一套任务系统。

现有 `AnalysisJobRequest.toJson()` 使用 `mode=standard`，不能直接当作新 `auto_analysis` 对象复用。应建立显式配置映射：首次常规批次采用协议允许的 `new_only`、`existing_result_policy=skip`，保留已选 grouping 和复制策略；导入前不发送 `selected` 或尚未存在的照片 ID。

一次开始操作建议持久化如下信息，设备身份为隔离键的一部分：

| 类别 | 必须保存的信息 |
| --- | --- |
| 用户意图 | 盒子身份、卡身份、批次名称、确认过的分析及复制配置、记录格式版本 |
| 项目创建 | 固定创建幂等键、完整请求、状态、已确认的 project ID |
| 导入提交 | 固定导入幂等键、包含 auto_analysis 的完整请求、发送及回包确认状态 |
| 流程关联 | contract、owner、import job ID、analysis job ID、可选 follow session ID、最后权威快照及时间 |

项目创建键和导入键分别固定，不能复用同一个键表示两个端点的不同操作；各自首次发送前落盘。保留新协议原始响应封套的专用路径，现有端点默认拆 `data` 的行为不全局改变，以降低影响面。

`owner=box` 时，导入完成回调及刷新路径只刷新流程，不再调用 `createAnalysis` 或 `startStaged`。持续复制接回盒子已登记的唯一 session，保留用户选择。重开和回网先按盒子身份查询 `GET /api/v1/projects/{project_id}/import-analysis`；POST 同键重放后必须再 GET，因为重放结果可能是首次快照。

`waiting_import` 显示等待导入；`dispatch_state=dispatched` 不等于 AI 完成。无候选时按协议显示识别任务已完成且没有可处理照片，不启动 pipeline。识别取消使用预登记 analysis ID、当前 job version 和固定动作键；服务确认前显示待确认。`import_analysis_owned` 接回原任务，来源卡变化明确停止，`backend_restarted` 明确中断，不自动重建。

旧盒子缺能力时保留旧流程并准确表达能力边界。已选择新协议的请求失败，不删除 `auto_analysis` 或复制配置后静默提交旧流程。

## 已实现的行为

| 场景 | 本次处理 |
| --- | --- |
| 多张照片版本不同 | 同一业务操作只取一次项目 CAS，选中照片不再按照片版本拆请求；单张审阅继续使用照片版本 |
| 批量动作 | 未标记、保留、弃选、精选、添加标签、删除标签统一走项目批量入口；标签因每张原有标签不同保留业务差量组，以支持精确撤销，每组均取项目 CAS |
| 成功回包 | 严格解析项目 `version`、显式成功与失败 ID；未确认的 ID 保留为失败，不推定整批成功 |
| 缓存与后续单张保存 | 清除旧详情、分组、候选查询和旧内存审阅版本；成功照片通过既有详情 GET 获取各自权威版本，串行合并共享页缓存，不把项目版本写成照片版本 |
| 在线请求结果不明 | POST 前持久化原参数及稳定幂等键；发送标记先落盘。回包丢失、格式不明及重开 App 均沿用原键、原参数重放 |
| 写入已确认但补读失败 | 先持久化批量回执，再核对照片缓存；保留修复记录，重连只补 GET，不再次 POST。旧回执只读当前状态，不在手机重新套用旧动作；已确认成功的照片不显示为待写入 |
| 真实项目 409 | 保留原意图并转冲突，明确提示核对；不拿 `current_version` 自动重写。标签及撤销发生冲突后停止后续组 |
| 部分成功 | 原完整请求和回执一起保留，待处理 ID 仅为未成功项；成功照片不重复提交，不自动改成子集换新键 |
| 接受盒子内容 | 从权威详情刷新失败项后才移除冲突；已删除照片只移除本地缓存行，无盒子删除动作。批量冲突可从相册进入现有同步处理页 |
| 多个离线动作 | 仅用本机已确认的前序 CAS 推进同基数、尚未发送的新格式后续草稿；已发送、真实冲突、旧格式记录均不自动换版本 |
| 旧离线批量队列 | 缺格式／作用域标识时保留原意图、键及参数并转冲突，等待重新核对；不把旧照片版本猜成项目版本 |
| 并发与换盒子 | 同设备命名空间／项目串行处理新提交和同步；同步按最新存储快照处理，保留已写回执。项目读取期间切盒子阻止向下一盒子发送 |

离线标签保持原有“等待确认后再合入权威标签缓存”语义；已排队不等于盒子已经确认。即时筛选投影仍属于 B2.3。

## 持久化与恢复规则

新批量记录增加 `schema_version=2`、`version_scope=project`、`request_sent` 和可选 `batch_receipt`。`payload.version` 与记录的 `version` 必须一致，盒子／项目身份必须完整。旧记录默认未知作用域，不自动迁移成可发送记录。

请求恢复顺序为：保存完整意图 → 保存已发送标记 → 同键 POST → 保存回执 → 缓存失效与权威补读 → 全成功时删除记录。部分失败记录保持冲突；全部成功而缓存未修好时保留回执供只读修复。批量同步在项目锁内读取最新记录，通用同步器不在锁外用旧批量快照写入 syncing 状态；同步失败及授权失效处理也使用最新记录，不覆盖已经保存的回执和发送标记。

自己的确认回包只允许推进后续未发送的新格式草稿；它不是“任何 409 都刷新重试”的通道。外部修改仍触发真实 CAS 冲突，部分失败需要用户核对；重新确认是新的用户动作，才产生新键。

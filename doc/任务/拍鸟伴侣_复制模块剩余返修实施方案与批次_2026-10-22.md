## 1. 结论与本轮目标

沿用现有 RC3 复制架构，在组员已经完成的返修上增量实现。目标是让用户在设备正常、网络波动和设备离线时，都能确认复制范围、读取同一个任务，并看到有接口依据的状态与结果。

建议按 B0～B6 共七批推进：B0 核对基线与真实响应；B1 补齐任务恢复；B2 修连接状态收敛；B3 修预检失效与设备选择；B4 修计划明细与数量一致性；B5 修名称、阶段、耗时与速度；B6 做联合验收与交付。

全部批次由你一人串行完成，每次只推进一个可验证的小改动。先完成复制任务读取与恢复，再集中处理全局连接，随后连续处理配置与预检，最后统一处理详情展示。B5 的接口确认从 B0 开始记录；缺少真实响应只阻塞依赖该字段的部分。`app_dependencies.dart` 按批次最小接线，不能同时夹带多个未验收模块的修改。

## 3. 实施约束与共用设计

### 3.1 三类状态各自有唯一归属

| 状态 | 归属 | 页面职责 |
|---|---|---|
| 可信设备、连接轮次、认证结果 | 现有 session / connection 模块 | 订阅并展示，不自行宣布全局连接成功/失败 |
| 复制配置、预检有效性、对账结果 | CopyConfigCubit 与可测试的计划汇总逻辑 | 展示禁用原因与恢复入口 |
| job_id、最新详情、刷新策略、附属数据错误 | CopyJobDetailCubit 及活动任务记录 | 展示快照、进度、操作与重试 |

复用现有 generation、CancelToken、SessionRefreshCoordinator 和缓存接口。`attempt_id` 用于诊断关联，generation/cancel 负责实际隔离；仅添加一个 ID 不会自动解决竞态。

### 3.2 接口事实和 App 展示分开

- `plan_state` 决定某个计划项会复制、跳过、不适用还是阻止；冲突策略不等同于该项执行结果。
- 逻辑照片、物理文件、计划项不是同一个计数单位。RAW+JPEG 可能一张照片对应多项，不得直接把“5 张照片”当作“5 个文件”。
- 字段缺失与数值为 0 分开处理。尤其 review_export.enabled 缺失不能默认为 false，速度缺失不能显示 0 MB/s。
- 对 timing、阶段状态、冻结名称，先写明来源与语义，再渲染。缺字段显示“暂不可用/状态未知”，不能从事件文本、客户端轮询间隔或旧任务偏好推导。
- 后端已修复 recognized_assets / filtered_assets；App 继续提交完整筛选快照，不用当前页照片 ID 替代后端匹配集合。

### 4.2 每次开工与收工的固定动作

每次开工：

1. 看 git status 和上一个提交，确认没有把本机配置、诊断输出和无关改动混入。
2. 从清单选当前一小步，用一句话写本次用户可见变化及其验收方法。

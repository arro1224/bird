审计方式：只读检查 APK、后端源码、交付说明、既定 RC3 复制协议及 K7 当前运行状态；本次未向板子部署或覆盖文件。

## 1. 总结结论

v6 暂不能按“BLE 和复制功能全部完成”验收，也不应直接照随包 systemd 模板部署。

- BLE：APK 内已经加入 Android Bond、加密写入前检查、断线重连、重新订阅通知和分片响应处理；UUID 与 K7 当前服务一致。代码层修复成立，但尚未用该 APK 在真实手机与当前 K7 上完成最终连接验收。
- 普通复制：`selected_assets`、`filtered_assets`、`recognized_assets`、`batch_all_assets` 四种范围已有真实预检、持久化任务和文件复制执行代码，不是纯界面或 mock。
- 完整 RC3：没有完成。`media_full_backup` 被明确禁用；识别/审阅变化后的元数据更新是零项目、立即完成的占位实现；App 没有接入 RC3 任务详情、进度、事件、报告、暂停、继续、取消、失败项重试和安全移除。
- 板端：之前实现的 `/home/kickpi/box_backend` 是可复用的底层存储执行器，功能比 v6 上层目前实际调用的更多，不应删除或覆盖。当前旧 API 没有 RC3 业务接口，后续确实需要部署新的 API 业务层。
- 部署：v6 附带的是系统级服务模板，但当前 BLE 与 API 是用户级服务，并通过 `/run/user/1000/birdbox/` 下的 socket 连接。直接套用模板会造成 BLE 找不到新 API。

## 3. 阻止完整验收的问题

### P0-1：后续元数据更新是占位接口，却被声明为已就绪

既定方案要求：照片复制后，即使识别或人工审阅稍后发生变化，也能只更新目标盘已有副本的 XMP、CSV或可嵌入字段，不重新复制原图。

v6 当前行为：

- 能力接口返回 `metadata_export_ready=true`，并在 features 中声明 `metadata_export`；
- 可用性接口永远返回 `has_changes=false`、`can_preview=false`；
- 元数据预检永远为 0 项；
- 创建更新任务后立即返回 `completed`，仍为 0 项；
- items/events/report 均为空或复用占位摘要；
- App APK 中完全没有 metadata-update API 调用。

这会造成三端误判“已成功更新”，实际目标盘没有发生任何变化。该能力必须真实实现；在实现前必须把能力标志改为 false，并从 features 移除，不能冒充完成。

证据：`backend/birdbox_backend/rc3_copy.py` 第 97～108、514～515 行；`backend/birdbox_backend/main.py` 第 1464～1535 行。

### P0-2：整卡摄影资料全量备份未实现

既定设计中的 `media_full_backup` 是独立于识别批次的整卡摄影资料备份，用户无需先建批次或等待识别。

v6 将该范围从 `SUPPORTED_SCOPES` 移除，并始终返回 `capability_unavailable`。交付说明也明确说本轮不实现。因此它不能被称作完整复制功能交付。

板端其实已经实现持久化摄影文件扫描接口：`photography.scan`、`photography.scan_page`、`photography.scan_delete`，并支持 100000 文件上限。当前缺的是 v6 API 业务层对这些能力的编排和 App 的可执行闭环，不是 K7 完全没有底层能力。

证据：`backend/birdbox_backend/rc3_copy.py` 第 26～28、289～302、411～416 行。

### P0-3：App 创建任务后没有接入任务生命周期

App 当前能创建 RC3 复制任务，但 `CopyApi` 只实现到 `createJob`。APK 内未实现以下 RC3 调用：

- 复制任务列表与任务详情；
- items、events、report；
- pause、resume、cancel、retry-failed；
- metadata update；
- safe-remove。

创建成功弹窗虽然写着“任务进度与结果可在任务中心查看”，源码注释却明确写着“后端交付后在此接入查看任务进度跳转（阶段 D）”，弹窗按钮仅关闭页面。通用 `/api/v1/jobs` 使用另一张 jobs 表，不会自动包含 `copy_jobs_v1` 中的 RC3 复制任务。

结果是：文件可能在盒子后台复制，但用户无法按 RC3 设计可靠查看、控制、恢复或验收该任务。

### P0-4：随包服务模板与当前 K7 的 BLE/API 拓扑不兼容

当前 K7：

- API 用户服务：`birdbox-api-v4-rc4.service`；
- BLE 用户服务：`birdbox-network-rc4-stage1.service`；
- BLE 依赖上述 API 服务；
- 二者通过 `/run/user/1000/birdbox/birdbox-api.sock` 通信；
- 稳定 device_id 位于用户目录并由两个服务共享。

v6 模板：

- 新建系统服务 `birdbox-backend.service`；
- 依赖并不存在的系统服务 `birdbox-network.service`；
- 使用 `/run/birdbox/birdbox-api.sock`；
- 使用 `/var/lib/birdbox/device/device-id`。

若直接照模板部署，新 API 与现有 BLE 会使用不同 socket 和不同 device_id 路径，BLE 配对/授权链路不会自动切换到新后端。部署必须继续沿用当前用户级服务拓扑，或一次性同步迁移 BLE 与 API；不能只换 API 模板。

证据：`backend/deploy/birdbox-backend.service` 第 1～15 行，以及板端当前两个用户服务的实际配置。

### P0-5：当前目标 U 盘写挂载授权异常

板端能识别：

- 源卡：`media_2d6dee77bb5ecc73e3d34787`，只读，角色正确；
- 目标 U 盘：`media_7f9a76e6c97690b61aedf6fd`，角色正确。

但目标 U 盘当前也挂载为只读，`birdbox-media.service` 日志反复出现 `UDisks2 authorization denied`，且系统中未找到 BirdBox Polkit 规则。存储层设计会在取得写租约时临时切到可写，但现状很可能在这一步被授权拒绝。部署前必须补回受限 Polkit 规则，并做一次真实 `target.acquire → file.copy → target.release` 验收；不能放宽全局挂载权限。

## 4. 其他需要修正的问题

### P1-1：能力状态是硬编码，不反映板端真实状态

`copy-capabilities` 直接返回 `storage_ready=true`、`copy_ready=true`，没有先调用底层 `capabilities.get`。即使 socket 不存在、目标写入授权失效或协议版本不匹配，App 仍会先看到“复制已就绪”。

### P1-2：批次源卡绑定不严格

传入 batch_id 时，后端仍直接选择发现列表中的第一张源卡，没有校验该批次是否确实来源于该 media_id。换卡后可能直到逐文件复制才失败，不符合“任务创建前锁定正确源卡身份”的设计。

### P1-3：目标推荐原因错误且 App 没读取后端推荐

没有历史成功目标时，后端会自动拿第一个目标盘，却把原因标成 `last_successful_target_for_batch`。同时 App 的 `lastSuccessfulTarget()` 固定返回 null，只把目标偏好保存在手机本地。卸载 App、换手机或多客户端后会丢失。

### P1-4：预检清单无法检查

预检汇总有数量和容量，但 `/copy-previews/{id}/items` 永远返回空列表，无法分页检查冻结后的实际目标文件名、冲突决定和来源映射。

### P1-5：进度时间数据是假值

复制任务的 `elapsed_seconds`、`active_seconds`、`bytes_per_second` 始终为 0，ETA 始终为空，当前项也始终为空。任务可以复制，但 App 无法提供可信进度。

### P1-6：偏好版本和幂等覆盖不完整

偏好保存采用“先读再写”，没有在同一事务中做条件更新；任务创建只记录 `expected_preferences_version`，未再次验证。部分 RC3 POST 端点也没有完整执行服务端幂等回放。

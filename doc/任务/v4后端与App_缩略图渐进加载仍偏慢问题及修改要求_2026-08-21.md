# 拍鸟盒子 v4：缩略图渐进加载仍偏慢问题及修改要求

日期：2026-08-21  
适用对象：App 开发、盒子 HTTP 后端开发  
测试版本：板端 `birdbox_api_v4_0_6_3`  
测试介质：同一张相机存储卡，共 14 张 ARW 原图

## 1. 结论先行

v4 已经解决了“必须等全部缩略图生成完，App 才能看到任何图片”的主要问题：缩略图现在会逐张发布，App 可以渐进显示。

但用户仍会感觉慢，原因并不在 RKNN 识别本身，而主要在识别完成后的缩略图链路：

1. 后端为了不抢占识别资源，会等 RKNN 分析结束后再集中生成缩略图；
2. 目前只有一个低优先级后台工作线程，14 张 ARW 基本逐张串行处理；
3. 每张 ARW 都需要打开、提取内嵌 JPEG、解码、缩放到 512 像素、重新编码、落盘并登记数据库；
4. 同一张卡、同一批未变化的照片再次建立项目时，第二次仍然 14 张全部重新生成，缓存命中数为 0；
5. App 端在此前同版本测试日志中存在同一缩略图地址被重复请求的现象，会放大“逐张出现”和刷新延迟；
6. 后端还为每个项目生成约 68 MB 的 2048 预览图。预览图排在缩略图之后，通常不直接阻塞首张缩略图，但会持续占用存储和 I/O。

因此，本轮优化重点应是“复用未变化图片的已有缩略图 + App 请求去重 + 缩略图有限并行”，不应修改 RKNN 模型、识别阈值或现有 pipeline 算法。

## 2. 本次真实测试情况

### 2.1 测试环境

- KICKPI K7，RK3576；
- 手机开启热点，盒子连接该热点；
- 使用另一部手机打开 App 后，mDNS 已能发现盒子；
- 相机卡只读挂载；
- 卡内 14 张 ARW；
- 两次测试使用的是同一张卡和同一组照片；
- v4 后端、现有 `box_backend` 和 `china_v6/pipeline.py` 共同完成流程。

### 2.2 两次测试数据

| 指标 | 第一次测试 | 第二次测试 |
|---|---:|---:|
| 扫描及建立索引 | 0.888 秒 | 1.055 秒 |
| pipeline 报告墙钟时间 | 3.933 秒 | 3.919 秒 |
| 点击分析到结果完成 | 6.435 秒 | 6.654 秒 |
| 后台派生图总耗时 | 27.631 秒 | 28.124 秒 |
| 派生图任务记录的首张缩略图时间 | 7.242 秒 | 7.269 秒 |
| 相对“识别结果完成”后的首张缩略图等待 | 约 1.48 秒 | 约 1.49 秒 |
| 14 张缩略图从第一张到最后一张的跨度 | 10.612 秒 | 10.768 秒 |
| 缩略图失败数 | 0 | 0 |
| 第二次相同图片缓存命中 | — | 0/14 |

注意：“派生图任务记录的首张缩略图时间”从后台任务开始计时，里面包含等待分析任务让出资源的时间。对用户更直观的数据是：识别结果完成后约 1.5 秒出现首张缩略图，但所有 14 张显示齐仍需约 10.6～10.8 秒。

### 2.3 存储占用

- 单次 14 张缩略图合计约 0.44 MB；
- 单次 14 张 2048 预览图合计约 68.3 MB；
- 两次相同测试仅预览图就重复占用约 136.5 MB；
- 两次均显示 `cache_hit_count = 0`。

这说明缩略图文件本身并不大，慢主要发生在 ARW 打开和派生图制作过程；与此同时，预览图的重复生成是更明显的板端存储问题。

## 3. v4 已经改对的地方

以下功能应保留，不要回退：

- RKNN pipeline 运行期间优先保证识别吞吐；
- 缩略图生成后立即登记并发送 `asset_ready`，不再等全批完成；
- App 可以逐张获得缩略图；
- 缩略图和预览图均来自相机卡原图，原图不复制到板子；
- 对外仍使用文件 ID 和 HTTP 接口，App 不接触 Linux 绝对路径；
- 相机卡继续只读，不向卡内写文件；
- 单张派生图失败不会中断整批。

## 4. 原因分析

### 4.1 识别和缩略图是两条不同链路

14 张图片的 RKNN pipeline 墙钟时间约 3.9 秒，说明原有并行化和 NPU 优化仍然生效。用户在主页等待缩略图，不代表识别仍在慢慢运行。

当前顺序大致是：

```text
扫描相机卡
→ 建立 14 张图片索引
→ RKNN pipeline 识别
→ 结果入库并通知 App
→ 后台逐张打开 ARW、生成缩略图
→ 每生成一张就通知 App
→ 缩略图完成后继续生成较大的预览图
```

所以“识别很快”和“图片墙显示齐较慢”可以同时发生。

### 4.2 后端当前基本串行生成缩略图

14 张缩略图从第一张到最后一张约 10.7 秒，相当于平均每张约 0.8 秒。对 50 多 MB 的 ARW，单张包含以下工作：

1. 打开 ARW；
2. 定位并提取内嵌 JPEG；
3. 解码内嵌 JPEG；
4. 按 512 像素规格缩放；
5. JPEG 重新编码；
6. 原子写入缓存目录；
7. 计算/记录派生图信息；
8. 更新数据库并发送资源就绪事件。

这些步骤单张并非异常慢，但 14 张串行叠加后，用户会明显看见图片逐张出现。

### 4.3 相同原图没有跨项目复用缓存

两次测试使用完全相同的卡和照片，但第二次依然生成了全部 14 张缩略图和 14 张预览图，缓存命中为 0。

根因是当前派生图缓存身份仍与“本次项目内新生成的 `file_id`”绑定。相同物理文件在新项目中会得到新的 `file_id`，因此即使来源路径、大小、修改时间和快速指纹都没变化，也无法命中上一项目的派生图。

这不符合产品期望。用户再次插入同一张未变化的卡时，应复用已有缩略图；只有新增或实际变化的图片需要新生成。

这里不需要引入复杂的全文件 SHA 或复制原图。可以复用现有索引信息构成稳定缓存键，例如：

```text
media_id
+ source_key / 相对路径
+ 文件大小
+ mtime_ns
+ 现有 quick_hash（如已有）
+ 派生图规格版本（例如 thumb_512_v1）
```

数据库中的项目文件仍保留各自的 `file_id`；只是多个 `file_id` 可以指向同一份稳定派生图缓存。

### 4.4 App 重复请求会放大等待感

此前同一 v4 版本的访问日志显示，部分缩略图地址在短时间内被请求两次。常见触发原因包括：

- 页面重建后重新发起请求；
- WebSocket 资源就绪事件和定时刷新同时触发加载；
- 列表滚动、筛选或状态刷新导致同一图片组件重新请求；
- 同一 URL 没有共享“正在请求中的 Future/任务”；
- 图片缓存键不稳定。

即使后端具备磁盘缓存，重复 HTTP 请求仍会增加解码、网络和 UI 刷新负担。

### 4.5 2048 预览图体积过大且重复

当前预览图采用 ARW 内嵌 JPEG 直接输出，因此 CPU 开销相对小，但得到的文件可能仍接近原内嵌 JPEG 尺寸。本次每个项目约 68.3 MB，两次相同项目重复约 136.5 MB。

预览图不应成为首页缩略图显示的前置条件。建议将其改为：

- 用户点开单图详情时按需生成；或
- 后台最低优先级生成，但跨项目复用；
- 若 App 实际只展示 2048 以内图像，应真正限制最长边和质量，而不是把大内嵌 JPEG 原样保存为“preview”。

## 5. 后端必须修改的内容

### P0：优先完成

#### 5.1 增加跨项目稳定派生图缓存

- 缓存键不得只依赖项目内 `file_id`；
- 使用稳定介质身份、相对路径、大小、时间、已有快速指纹和派生图规格；
- 新项目扫描同一张未变化的卡时，把新 `file_id` 映射到已有缓存；
- 新增照片只生成新增照片；
- 文件内容发生变化时必须失效并重新生成；
- 不复制 ARW 原图，不向相机卡写入任何数据；
- 记录 `cache_hit_count`、`cache_miss_count` 和失效原因。

#### 5.2 缩略图与预览图分级

- 缩略图属于 P1 资源：结果完成后尽快提供；
- 预览图属于 P2 资源：不阻塞首页，优先按需生成；
- 不得因为预览图未完成而让缩略图接口返回不可用；
- 不得在每个新项目中重复保存相同来源的 68 MB 预览图。

#### 5.3 补齐可观测时间

每个项目至少记录：

- `analysis_finished_at`；
- `first_thumbnail_ready_at`；
- `all_thumbnails_ready_at`；
- `first_preview_ready_at`；
- `all_previews_ready_at`；
- 每张图的 ARW 打开、提取、解码、resize、encode、write、DB/event 耗时；
- 缓存命中/未命中数量；
- 派生图队列长度和 worker 数。

这些字段可以先写入性能报告或日志，不要求立刻改变 App 公共接口。

### P1：完成 P0 后评估

#### 5.4 缩略图有限并行

- RKNN 分析期间仍保持低资源占用，不抢 NPU pipeline；
- 分析结束后，先从 2 个缩略图 worker 开始验证；
- 只并行缩略图，不同时并发大量 2048 预览图；
- 不要直接扩到 4～8 个 worker，避免 ARW 解码造成内存峰值和 I/O 抖动；
- 用同一组 14 张 ARW 对比 1 worker 和 2 worker 的墙钟时间、内存和温度，再确定默认值。

## 6. App 必须修改的内容

### 6.1 同一缩略图请求去重

- 同一 `file_id + thumbnail spec` 在已有请求进行中时，共享同一请求，不再启动第二次；
- 对成功结果使用稳定缓存键；
- 页面重建、Tab 切换、过滤和列表滚动不能无条件清空图片缓存；
- 收到 `asset_ready` 时只刷新对应图片项，不刷新整个图片列表；
- WebSocket 推送和轮询不能同时对同一资源触发加载。

### 6.2 正确使用 HTTP 缓存

- 保留并使用后端的 `ETag`；
- 对已缓存图片发条件请求，允许 `304 Not Modified`；
- URL 或缓存键只有在图片版本实际变化时才变化；
- 资源未就绪时显示占位图，按 `Retry-After` 或有限退避重试；
- 不要高频无限轮询。

### 6.3 页面显示策略

- 项目和识别结果可以先显示文字状态；
- 缩略图就绪一张显示一张；
- 不等待 2048 预览图；
- 单图详情页打开时再请求预览图；
- 如果详情图尚未生成，先显示 512 缩略图，再平滑替换成预览图。

## 7. 三端接口原则

本轮优化不需要推翻现有接口。应继续使用现有语义：

- `thumbnail_status`；
- `preview_status`；
- `asset_ready`；
- 缩略图/预览图 HTTP 地址；
- `ETag`；
- 资源未就绪时的明确状态码和 `Retry-After`。

后端内部改变缓存键时，不要把 Linux 路径暴露给 App，也不要让 App 自己拼接缓存路径。

## 8. 验收标准

固定使用本次同一组 14 张 ARW，分别进行冷缓存和热缓存测试。

### 8.1 冷缓存首次运行

- pipeline 墙钟时间不比当前约 3.9 秒退化超过 10%；
- 点击分析到结果完成保持在约 7 秒内；
- 识别完成后首张缩略图目标不超过 2 秒；
- 14 张冷缓存缩略图显示齐目标 5～7 秒内；
- 0 张缩略图失败；
- App 对每张缩略图正常情况下最多发起 1 次有效下载请求。

### 8.2 热缓存再次运行

- 不更换卡、不修改照片，再建立项目或重新进入项目；
- 14 张缩略图缓存命中应为 14/14；
- 不重新解码 14 个 ARW；
- 后端资源状态应接近立即就绪，目标 1 秒内完成映射；
- 预览图不得再额外重复占用约 68 MB；
- App 不因页面重建重复下载已缓存缩略图。

### 8.3 增量场景

- 在卡中新增 1 张图片后扫描；
- 原 14 张应继续命中缓存；
- 只为新增 1 张生成缩略图和预览图；
- 修改或替换原文件时，仅对应文件缓存失效；
- 拔卡、换卡、断网和 App 重连不能损坏已有任务记录。

## 9. 后端与 App 需回传的验收证据

后端提供：

- 冷缓存、热缓存、增加 1 张图三组性能报告；
- 每组 `cache_hit_count/cache_miss_count`；
- 首张和全部缩略图时间；
- 预览图占用空间；
- 1 worker 与 2 worker 的内存和墙钟对比；
- 没有修改 RKNN 模型、阈值和 pipeline 输入协议的说明。

App 提供：

- 同一项目首次进入和再次进入的网络请求日志；
- 每个缩略图 URL 的请求次数；
- WebSocket `asset_ready` 到对应单项刷新的日志；
- 页面滚动、切换 Tab、返回页面后不重复下载的验证；
- 资源未就绪时的占位和有限重试录屏。

## 10. 本轮明确不做的事情

- 不修改鸟类识别模型；
- 不修改分类、检测阈值；
- 不取消相机卡只读挂载；
- 不把 ARW/JPEG 原图复制到板子；
- 不让 App 读取板端绝对路径；
- 不引入没有必要的复杂全文件哈希流程；
- 不以增加大量 worker 的方式盲目换速度；
- 不让缩略图优化影响当前约 4 秒的 14 张 RKNN 吞吐。

## 11. 完成定义

只有同时满足以下条件，才算“缩略图慢”问题完成：

1. 首次冷缓存时，缩略图能稳定渐进显示且整体时间明显缩短；
2. 同一张未变化的卡再次使用时，14 张缩略图不再重新生成；
3. App 不重复请求同一缩略图；
4. 预览图不阻塞首页，且不在每个项目重复占用约 68 MB；
5. RKNN 识别速度不退化；
6. 新增、替换、换卡等场景不会错误复用旧图。

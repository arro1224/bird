## 一、接续 11-17 遗留：「获取预检并继续」按钮闪烁——已定性并修复

### 排查过程

- 昨日怀疑方向（`_readDevices` 每轮 `emit(refreshingDevices: true)`）方向正确，但细看后主按钮可以排除：`canFetchPreview` / `environmentBlockReason` 都不依赖 `refreshingDevices`，正常轮询不会灰主按钮——与昨日像素采样「绿色占比恒定 0.6%」互相印证（0.6% 不是满宽 54px 主按钮的量级，说明采样窗口里变的不是主按钮）。
- 真正的闪烁源是**紧邻主按钮的「重新检测设备」TextButton**（`copy_confirmation_page.dart:1255`）：它把 `onPressed` 和文案绑在 `state.refreshingDevices` 上，而 `_readDevices` 每轮 pollInterval（4s）开头 `emit true`、结束 `false` → 按钮每轮灰一下 + 文案在「重新检测设备/正在检测设备…」间切换。
- 排除项：`DeviceSessionCubit` 无周期 timer，`sessionChanged()` 在可用性不翻转时早退，`canFetchPreview` 不会经会话链抖动。
- 顺带发现 `setAppLifecycleActive` 注释写「回前台静默刷新」，实际也翻转 `refreshingDevices`（每次切后台回来闪一次），一并修了。

### 修复（`3db6e44f2`，已推送）

`refreshDevices` 增加 `silent` 参数：**后台轮询、事件驱动刷新（`_requestRefresh`）、回前台宽限刷新（`_refreshAfterResume`）三条后台路径不再翻转 `refreshingDevices`**；手动点击与预检/提交内刷新保留原有反馈。手动刷新合并到在途读时补点标志，避免点击无响应。

- 守护测试：后台轮询数轮后 `refreshingDevices` 恒 false、手动刷新仍点亮、静默刷新不销毁有效预检。
- 测试基线：b3 文件 38 过；copy 目录 307 过 / 4 跳过全绿；`flutter analyze` 无问题。

### 排查方法论

## 二、任务主页「当前任务」卡片返回后进度从 0 稳步爬到 100——已定性并修复

### 现象（用户口报澄清）

检索（AI 分析）任务在详情页已 100%，按左上返回任务主页，上方「当前任务」简略卡片**才开始从 0 稳步涨到 100**。

### 排查过程（先排除，再实锤）

**排除项**：
- 页面/组件层无任何动画代码（全局搜 `Animated*`/`AnimationController` 仅一处无关 `AnimatedContainer`）
- SDK 3.44.5 源码确认 determinate `LinearProgressIndicator`（传 value）无挂载动画，直接渲染
- 主页卡片与详情页共用同一 `RepositoryTaskExperienceController`，且 IndexedStack 让主页常驻监听——数据同源同帧
- mock 侧全部正常：每条 `job_updated` 带完整 Job + version 递增；`_createWorkflowJob` 有 409 去重；SmartFollow 子任务不进通用 `_jobs` 表

**复现实锤**（新写集成测试，真实 mock + WS）：
- WS 正常链路 2 用例全过——数据链本身无 bug
- **WS 断连场景**：断开 WS 后 REST 轮询链路正常但**采样极慢**——修复前 16s 只爬到 13%，序列 `[0×6, 4×9, 13×5]`

### 根因（两层叠加）

1. **WS 无心跳**：`IOWebSocketChannel.connect` 从未设 `pingInterval`（默认 null）——Wi-Fi 抖动/省电断 TCP 后双方都不知情，**僵尸 WS** 让 App 状态一直显示 connected；而 `_configurePolling` 见 WS connected 就**不启动 REST 轮询** → 事件流静默死亡时任务进度完全失去更新来源。
2. **退化轮询太慢**：WS 断/重连耗尽（maxAttempts 5，31s 退避）时虽有 4s REST 轮询兜底，但 `refreshFromBox` 串行 6+ 请求，进度每 4~8s 才跳一格。详情页的 100% 来自**进页时 `refreshJobDetail` 的 REST 单点读**；返回主页后轮询链路逐帧追赶 →「从 0 稳步涨到 100」。

### 修复（`9a9ffc141`，已推送）

- `EventClient` 增加 `pingInterval: 20s`：半开连接两个周期内暴露，走既有重连与恢复链路（WS 恢复成功即全量快照收敛）。
- `_configurePolling` 退化态轮询 4s → 1.5s。`pollInterval` 公开参数保留（@Deprecated）做兼容。
- 新增 2 测试文件 4 用例：WS 正常链路（不二次爬坡/快照单调）+ WS 断连链路（轮询接管/单调收敛到 100/completed 不回退）。
- 测试基线：tasks 80 过；core+features 1528 过 / 8 跳过全绿；analyze 无问题。

### 排查方法论

口报「爬坡」先分流：**像动画（1s 内滑过）= UI 动画；一格格跳（秒级）= 数据链路**。本次「稳步涨」秒级节奏直接指向数据采样，SDK 源码核查（determinate 无挂载动画）避免了在 UI 层浪费时间。集成测试复现比静态推演有效得多——静态推演出过 3 个自洽但错误的假设，最后是测试数据 `[0×6, 4×9, 13×5]` 一锤定音。

## 五、任务模块演示链路排障（下午接续，真机 + Mock 实跑）

目标：让「导入 → 自动 AI 分析 → 边识别边复制 → 复制任务」能在老师验收时连续跑通。

### 5.1 设备身份不一致（配对后直连热点交接报错）

- Mock `--device-id` 手敲成 38 字符、指导书里更是 42 字符，而 App 常量是 **36 字符**（`bbx-` + 32 hex）→ 交接期 `prepareDirectApHttp` 严格比对失败，报「设备身份不一致，已停止连接」。
- **指导书本身是错误源头**：启动命令与 `--dart-define=BIRD_SIMULATED_DEVICE_ID` 两处都是 42 字符；后者还会让 App **启动即抛异常**（`SimulatedBirdBoxDebugConfig.parse` 有 `^bbx-[0-9a-f]{32}$` 校验）。
- 修复：Mock 启动时校验 `--device-id`（不合法直接 exit 2）、横幅打印 `Device ID: … (36 chars)`；指导书改回 36 字符并删掉冗余 dart-define。

### 5.2 「边识别边复制」的 AI 分析永远 0/60

- `_tickWorkflowJobs` **刻意跳过**带 `smart_follow_session_id` 的分析任务（防会话快照撕裂），其进度只能由 `POST /mock/control/smart-follow` 驱动；演示现场没人 curl 它 → 永久 0%。
- 修复：Mock 新增 `--auto-smart-follow`，每 1s 自动 `commit` 一批（复用同一状态机），60 张约 8s 识别完并自动 draining → complete_children。指导书标注**必须带**。

### 5.3 导入 100% 后不自动级联 AI 分析（本次最严重）

- 代码：`_createAnalysisForCompletedImports` 先把「已存在分析任务的 project」塞进 `_analysisRequestedProjects`，随后 `if (!_analysisRequestedProjects.add(projectId)) return;`。该集合**只增不减**（仅出错时移除）。
- Mock 无持久化 → 重启后 `project-0001` / `job-analysis-0002` 这类 id 被回收复用；App 本地缓存/内存里的陈旧记录把新批次的级联永久挡死。实测：导入 60/60 完成，Mock **从未收到** `POST analysis-jobs`。
- 修复：改为**以盒子返回的权威任务为准**（`_jobs` 里已有同 project 的分析任务就跳过）+ 仅用 `_analysisInFlight` 做在途去重；`refreshJobDetail` 遇 404 时剔除幽灵任务；陈旧跟随配置（`recognition-option` 有值但无 staged/record）自动清掉并退回普通分析。
- 验证：真机两次实测 `POST /api/v1/projects/project-0001/analysis-jobs -> 202` **自动触发**，随后任务页「当前任务」自动变 AI 分析。

### 5.4 「复制照片」被判为「当前批次没有可处理照片」

- 门控只看 `currentProject.totalFiles > 0`。真机上导入完成后该摘要仍为 0（Mock 单测证明回填逻辑本身正常，60 会写进去）→ 入口置灰。
- 修复：任务首页能力解析加兜底——**该项目有已完成的导入任务且 `totalCount > 0` 就认定批次有照片**。
- 遗留：摘要为 0 的 App 侧根因未完全定位（缓存/时序），兜底已覆盖演示路径。

### 5.5 其它 Mock 保真度缺口（顺手补）

- `GET /api/v1/smart-follow-sessions` 列表路由缺失：队友 `d19b80bca` 的 `discoverSessions()` 每次进任务页吃 404，App 重启后跟随卡片不恢复。已补（`items/has_more/next_cursor`）。

### 5.6 配对失效后页面卡死

- App 在兑换授权前会**持久化消费**掉 pending 记录，失败后无法自愈；而失败页的「我已连接，继续验证」置灰，只有不显眼的文字按钮能退出。
- 修复：失败/超时态主按钮改为**「返回并重新配对」**；文案改为明确指出该点哪里。
- 另两个环境约束：模拟层配对码有效期 **2 分钟**；Mock 的配对会话**一次性**（同一进程内成功兑换过就不能再兑，换新 App 数据必须重启 Mock）。
